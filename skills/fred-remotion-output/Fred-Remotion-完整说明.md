## 每段先看候选，再定画面

Codex/助手常见问题是只用熟悉的两三个组件、或直接写大字页。每个需要画面的段落按下面顺序做，不跳步：

1. 在 Manifest 写 `componentPlan.query`：本段画面里**看得见的对象和动作**（例如“两个工具价格并排对比、数字落定”），不是照抄旁白。
2. 运行 `scene.py --manifest <path> --scene-id <id> --candidates-only`：给出按画面描述检索的 5 个候选，以及按旁白检索的 `narrationCandidates`。同类型不足时会跨类型补位并标注 `sameSceneType`。
3. 逐个看候选的准确视频或核心帧（`references.py --id <id> --full`），再按内容决定。前 3 个候选必须在 `componentPlan.candidates` 记录 `selected/rejected` 和具体理由；`library_gate.py --stage suggestion` 会重算并拦截漏记。原创授权段也要先比较。
4. 候选都不合适：先换个说法再查（拆成对象＋动作、换 `--use`），仍没有就报告缺口，不退成纯大字页。

按内容先查哪里（起点，不是固定搭配）：

| 口播在讲 | 先试 |
| --- | --- |
| 一句结论、关键词 | `--query 关键词 一句话`；多篇新闻反复出现同一个词用 NMC01 |
| 列举几个要点、能力 | `--query 要点 列表`、`--query 卡片 分类` |
| 步骤、流程、因果、架构 | `--query 流程 步骤`、`--query 分支 关系` |
| 两者对比、以前和现在 | `--query 对比 区别`、`--query 版本` |
| 输入提示词、聊天、回复 | INT03（Codex 操作）、INT04（可编辑微信）、CAM04；`--query 输入 发送` |
| 截图或文章里的某句话 | INT01（荧光笔）、INT02（蒙版聚焦）；`--use recording-focus` |
| 真实录屏操作 | CAM01–CAM05、`--use video-entry`；全屏播放用默认大播放组件 |
| 作品、多图、结果图 | `--use images` |
| 数字、价格、图表 | `--use data`、`--query 数据 增长`；这类组件很少，没有合适的就如实报告缺口 |
| 章节、转场、下一段 | `--use handoff`、`--query 转场` |

## 默认协作顺序

**稿件/可选录音 → 助手逐段图文建议 → Fred选方向 → 真实组件关键帧 → Fred提意见并确认 → 助手内部检查动态 → 完整视频 → 按意见局部返修。**

- 第一版页面就给有内容的建议：这句准备怎样讲、为什么适合、参考图片或可播放片段。能用准确库组件表达时先展示真实效果；需要新构图才生分镜图，不把空白设计任务交回 Fred。
- 方向确定后先实现足以渲染的真实组件，用本期文字/媒体和适用的角标/字幕出关键帧。关键帧用于改排版、主次、尺度、可读性和遮挡；随后内部看短动画、声音与接缝，再出完整视频。默认不额外等待一轮用户动态样片批准。
- 同一前端持续展示建议、关键帧与视频，保留版本和意见。默认用[公共审看模板](references/segment-review.md#公共模板默认)的初始化/更新/启动脚本，只换本期Manifest和媒体；音频模块沿用音频Skill公共台，不逐期重写页面。`assets/review-example-ep108/START.py`可直接打开108前7段61.47秒真实内容示例，含口播、字幕、关键帧及视频；它是可替换的示例数据，非固定每期画面方案。数量由内容决定，不固定九宫格、140张、组件配额或切镜频率。完整工作方式和字段见[路线、关键帧与确认](references/route-and-storyboard-review.md)。
- 已有明确方向/关键帧确认不重复问；局部返修只处理受影响内容。当前直出授权可覆盖用户审看步骤，记录真实来源与未审看范围；内部技术检查和必要动态检查仍执行，不把输出授权写成样片认可。出关键帧还是直接出片，按 Fred 当次要求执行，不额外提醒或劝阻（2026-10-12 Fred 明确）；没有说明时按上面的默认顺序先出关键帧。
- **把组件串成整期**（分段工程、录屏包装、段间交接表、全片去重、强调方式、渲染前动态自检）按[整期编排](references/episode-assembly.md)执行。给写分段代码的子任务的简报必须带上它的第2–7节和本期交接表。工程结构直接用[整期骨架](templates/episode-skeleton/README.md)（时间轴、段外壳、交接几何、分块渲染、音频和 BGM、推前端）；交付前按整期编排第 12 节检查。

## 做一整期视频：最短路径

Fred 说“直接做视频”“直接出片”时，按下面这条路做。它是把 116–121 期的做法整理出来的（成对样例、`readability_audit` 和骨架里的 episode-kit 是 2026-10-15 才补上的）。开头“先验收组件”一节的门禁照常执行，一步都不省；但门禁只证明来源合规，**不证明画面好**，质量要靠第 1、3、5、6 步：

1. **先看[好坏成对样例](references/paired-examples.md)**：同一句口播做对和做错各长什么样。
2. **工程从[整期骨架](templates/episode-skeleton/README.md)拷**，共享件直接用骨架的 `src/components/episode-kit/`（真实比例 Codex 框、黑胶囊、毛玻璃、章节头与章节过渡、大播放窗片段），只换本期常量。
3. **写整期简报**：按[简报模板](templates/episode-assembly-brief.md)逐句填动作表（对象 → 变化 → 证据在哪 → 观众看哪 → 交给谁）和交接表，过完五条自查再写代码。整期简报（分段方案、交接表、全片规则）的范例：[120 期](templates/examples/brief-ep120.md)、[121 期](templates/examples/brief-ep121.md)。
4. **逐段选组件并过门禁**：按上面“每段先看候选，再定画面”写 `componentPlan`，跑 `scene.py --candidates-only`，`library_gate.py` 在建议阶段和关键帧阶段都必须 PASS。
5. **场景为本期重写**：拆已认可组件的动作，每个场景第一行注释写动作来源；范例场景在 `templates/examples/scene-*.tsx`（只供阅读）。
6. **先做一段对照，再铺全片**；每段出关键帧和中间态，**自己逐张看图**，问题写到段号和秒数。
7. **1080p 预览后跑 `motion_audit.py` 和 `readability_audit.py`**，接缝每 4 帧拼一张图看；视觉验收和技术验收分开写。
8. 按[整期编排](references/episode-assembly.md)第 12 节做交付前检查，再出 4K60。

## 把用户要求带到每个实际镜头

组件适配的共享字体、全文原位强调及媒体接替见[复用图谱](references/component-reuse-map.md#共享适配工具)。`scene.py` 会带出本段 `componentAdaptation`，实施前核对同组字阶、内容职责、全文检查状态和对象级保护；准确参数来自当前内容，不固定单期字号、行数或组件组合。


用户已给出的镜头、文字、材质和保留要求是当前执行输入，不要求用户每期再写一篇详细提示词。先按[制作默认值](references/production-defaults.md#将要求落实到当前执行包)存入同一 Manifest 的 `designContract` 与受影响场景；实现时用 `scene.py --manifest ... --scene-id ...` 读取，确认整片要求、当前动作、素材和角标一起到达。修方向时同步更新旧动作描述，不能只改图片或版本号。

动作实现与返修按[具体状态检查](references/production-defaults.md#将流畅跟口播落实到可观察状态)核对连续轨迹、内容就绪再扩容、真实阅读窗口和同载体交接；版式已成立时优先按口播交换焦点，不自动重做布局。静态通过、技术通过和动态认可仍分别记录。

备料按[全稿的信息职责](references/production-defaults.md#按全稿的信息职责备料)区分现成效果示例、本期讲解素材与实际操作证据；返修按[已认可的维度](references/production-defaults.md#按认可维度保护基线)保护准确版本。“在上面基础上加蒙版／组件”按[实际末态交接](references/media-and-overlays.md#继承实际末态再交给前景)继承媒体、滚动和相机状态，不重新开场。

需要委派或从短指令接手时使用[制作执行摘要](templates/production-execution-brief.md)，填入本期路径、当前授权和保留范围；它引用当前事实源，不新增一套审批。代表镜头要验证“与要求和参考相比是否保住表达与质感”，技术 PASS 不能替代这一步。

## 完整视频的BGM默认

完整成片默认按[背景音乐](references/background-music.md)执行：Fred本机使用已调好音量的私人音乐，从0秒开始、内部选段补足长度，原声欣赏区间静音且音乐时钟继续，整片混音一次再封装。正常BGM轨线性音量1，不再次降分贝；最终总线按实际AAC峰值必要保护。本机绑定及音乐实体不分发、不自动上传；他人用`--bgm`自备音乐，仍可使用同样的延长/静音/混音能力。已经含BGM的成片和剪映回传音轨不重复添加，单独口播与组件诊断不默认加音乐。执行入口为`scripts/bgm.py`，能力包由`scripts/package_bgm.py`生成。

## 固定配音与整期组件分配

Fred后续自己的每期完整视频默认在自然断点复用一次[Skill／组件库过渡配音](references/fixed-skill-library-insert.md)：**只固定音频，动画每期更换**，使用Fred当期提供或指定的画面，不自动复用109期动画。新稿录音正文不再重复这四句；从manifest读取当前纯配音的真实采样时长，与当期动画安排时间轴（当前5.540秒，旧6.016秒混音只留历史），字幕样式和画面衔接按当期要求处理。本期已有相同配音时不重复加，不固定旧视频的362帧或插入镜号。插入前核对纯配音/动画SFX混音身份，整条及内部各句响度按音频Skill检查，必要时只做本期局部匹配，不叠加旧处理。

建议前同时做[整期组件分配检查](references/component-distribution.md)，不能只验收单镜头。`library_gate.py`的suggestion阶段已拦截缺少具体整期比较的重复组；保留连续对象、同职责外壳和有意呼应，不用次数配额强行换差的组件。相似但不同来源仍需实际视觉总览。

# FredTalk 视频设计语言

用于设计新的解释动画、新做组件，也用于适配现有组件。首次构思整片、设计原创场景或新做组件时读。第 2 节是固定规则（具体数值），其余各节是表达原则；本文不规定每期的布局、切镜次数或组件套餐。

当前依据：2026-09-30 Fred 授权沉淀的字体/对齐、浅紫重点、文件对象及媒体连续性反馈，以及2026-09-23的默认外观；第95期当前源映射/认可记录、第99期8条精选准确源码，以及视觉库当前保留的对象/文字动作。用户最新要求优先；旧参考的局部描边、紫色铺面、连线或章节标题不自动继承。准确复刻及已认可局部返修按当次保护范围执行。

## 1. 要稳定的是什么

可以把这套风格描述为：**黑白实体界面、文字主导、按内容连续变化的动效。**

- 黑白面、清楚的大字、克制的柔和阴影建立分量与层级；紫色指出当前关键点。
- 画面围绕正在讲的对象与关系组织，镜头让观众认清变化。不能仅凭黑白圆角或同一字体就称延续了质感。
- 外观和动作的逻辑保持一致；内容、构图、载体、方向、数量与节奏可以变化。纯大字、真实媒体、复杂流程各有适用时刻。
- 字、材质、物体位置、声音和镜头共同指向此刻的重点。不要让每层都独立抢注意力。

## 2. 固定规则（2026-10-12 Fred 要求固定）

这一节是硬规则。新做组件、原创场景、对已认可组件做二创，都按这里执行。

- 数值出处（取自哪个已认可组件的哪一行源码）见[视觉值出处](references/style-kit-sources.md)。
- 改这里的任何值，都需要 Fred 明确同意，同时更新 kit、`kit.lock.json` 和本节。
- 准确复刻、已认可组件的局部返修，仍按当次保护范围保留原值，不强行改成本节的值。

### 2.4 动效（曲线、时长、相机）

具体怎么写（帧驱动、过冲回落、同一进度、对象连续、裁切擦出、文字三件套、景深、相机）见[动效手法](references/motion-craft.md)。

| 项目 | 固定值 |
| --- | --- |
| 主曲线 | `p()` = bezier(.22, 1, .36, 1) ease-out：进入、落定、文字出现 |
| 对象搬移 | `q()` = smoothstep：缩放、位移、蒙版、换位 |
| 章节擦出 | `wipe()` = bezier(.65, 0, .2, 1) |
| 回弹 | `springAt()` = 1 − e^(−8p)·cos(9p)，0.5–0.8 秒，只在明确需要“落下弹一下”时用。**不用 Remotion `spring()`**，不加无理由的弹跳 |
| 相机 | `quintic()` 配合 `cameraTransform()`：移动约 0.6 秒，停稳阅读 0.85–1.65 秒，交替进行。推近以能读清为准，常见 1.3–1.6 倍，不超过让内容出画 |
| 典型时长 | 胶囊打开 0.8 秒；单项进入 0.38–0.42 秒；汇聚 0.72 秒；新消息 0.32 秒；页面擦除 20 帧 |
| 逐字 | `typed()`：标题约 10 帧/字，正文 5–7 帧/字（60fps） |
| 节奏 | 常规组件 5 秒；快过渡 1–3 秒。主体在 0.3 秒内开始出现；结尾至少 0.6 秒稳定阅读；不用全程慢漂移填时长 |
| 依次出现 | 按口播 cue 排；没有 cue 时，项与项相隔 0.5–1.2 秒，不要机械等距 |
| 口播对齐（kit v2） | 每个组件提供 `cues?: number[]`，用 `cueAt(cues, i, 默认秒数)` 取时间：有真实口播就按口播触发，没有就用默认节奏 |
| 进出场（kit v2） | 用 `Handoff` 包住组件内容，提供 `enter`（cut/fade/rise/grow）和 `exit`（none/recede/fade/cut/slide-left/slide-up）。组件自己的入场动作不变，Handoff 只负责接上一段、交给下一段；角标在 Handoff 外面，不跟着动 |
| 局部聚焦（kit v3） | `Spotlight({ rects, amount })`：整体压暗 0.6，只留强调区原亮度，圆角柔边，可配合推近。指出页面某处、某一行时的默认做法，替代黑框、紫框和白色模糊蒙版 |
| 无过冲落定（kit v4） | `settle(t, delay, duration)`：0→1 平滑到位、不回弹。成片里的入场和胶囊落定默认用它（119 期 Fred 嫌 `springAt` “进来之后抖动了一下”）；`springAt` 只留给 Fred 明确要“砸下来”的效果 |
| 音效时长（kit v4） | `Sfx` 的 `duration` 按 60fps 帧数写，kit 按工程帧率自动换算，30fps 预览和 60fps 成片音效一样长 |
| 随机 | 渲染必须确定：不用 `Math.random`，伪随机要用固定种子 |

### 2.5 呈现（一个组件做什么）

- **一个组件只做一个主动作。** 动作来自“观众要看懂的变化”（谁 → 变成什么），不来自“挑一个入场特效”。关系与动作的对应见第 3 节。
- **快过渡（1–3 秒）可以用粗大字或大胶囊**，但必须有黑窗或黑胶囊做容器，字粗、对齐、对比强。没有容器、位置乱跳、灰字对比弱、白底大面积留白，都不合格。
- **真实界面必须推近到能读清**，读完再回全貌或交出去。
- **材料到结论**：材料退后（蒙版 + 失焦 + 轻微缩小），结论在前景读清。旧文字要先退干净，不能在前景下面留残字。毛玻璃表达的是“材料 → 判断”：不能用纯色页换掉背景还声称保留了上下文，也不是每段都要加蒙版。
- **同一动作只换颜色、换素材、换场景，算重复。** 新做前先查库，有同动作的组件就复用，不新做。动作不同的同类组件可以并存，用来轮换。
- 不像 PPT：没有页眉、页码、英文眉题、装饰编号、状态小字。

### 2.6 音效

| 动作 | 音效（kit 短名 → 库编号） | 触发点 |
| --- | --- | --- |
| 胶囊、圆点、条目出现 | `pop` → SFX05 | 主体首次出现 |
| 主次交换、推近、接管 | `woosh` → SFX04 | 运动开始 |
| 短窗口进入、遮罩刷出 | `whoosh-short` → SFX01 | 运动开始 |
| 让位、展开、整组上移 | `slide` → SFX13 | 运动开始 |
| 结果落定 | 默认 `pop` → SFX05；全片最重要的 1–2 次结果才用 `ding` → SFX03 或 `notify` → SFX07（传 `keep`） | 落定 |
| 真实点击 | `click` → SFX09 | 点下瞬间 |
| 实际输入 | `typing` → SFX08，音量 0.4 | 只覆盖打字区间 |
| 新回复进入 | `message` → SFX15 | 出现 |
| 多对象聚拢 | 默认 `woosh` → SFX04；全片最多 1–2 次用 `gather` → SFX16（传 `keep`） | 运动开始 |
| 数字实际滚动 | 全片最多 1–2 次用 `scroll` → SFX19（传 `keep`）；不传 `keep` 时 kit 自动换成 `whoosh-short`，想静音就不写 Sfx | 只覆盖滚动区间 |

- 音量 0.5（打字 0.4），不超过 0.5；
- 一个主动作配一声，同时有多个动作时只给主交接一声，每个组件通常 1–4 声；
- 不按每个字、每帧触发；
- **全片限量（kit v3，Fred 2026-10-13）**：齿轮滚动声（`gather`、`scroll`）和“叮”成功声（`ding`、`notify`）在整期里很跳，每期各只留 1–2 处。kit 的 `Sfx` 默认把它们换成刷（`woosh`/`whoosh-short`）和嘟（`pop`），要保留的那一两处写 `<Sfx name="ding" keep />`。交付前统计全片带 `keep` 的数量；
- kit v3 的替换也作用于在 v3 工程里使用的已入库组件（本期适配副本），这是有意的：全片统一限量。要在某个组件里保留，就在本期副本里给那一处加 `keep`，入库原版不改。
- 绑定细则见[音效](references/sound-effects.md)。

### 2.7 内容

- **默认内容用 Fred 的真实素材**：真实界面截图、作品、头像与 3D 卡通形象、真实 Logo、真实数据。不用 lorem、占位图或编造的界面。
- **所有可变内容都是 props**：文字、数量、素材、强调词、时间点。组件内部不藏旧常量。
- **长短文案都要能放下**：至少测一份更长、一份更短的文案。
- **安全**：
  - 密钥、令牌、密码从第一帧起打码；
  - 不出现手机号、私人聊天、他人隐私；
  - 他人创作的素材（例如 Library 的参考帧）不作为默认内容。
- **中文优先**：标签写“第一部分”，不写“PART 01”。产品名、代码、命令保持原样。
- **紫色强调词**由 props 指定（`highlight`），一句话里只强调一处。

## 3. 用关系组织动作

设计时先回答：观众已认清什么，接下来哪种关系发生变化，什么时候需要读完，下一段接走什么。动作不从“随机挑一个入场特效”开始。

| 内容关系 | 可复用的动作逻辑 | 质量锚点与适配要点 |
| --- | --- | --- |
| 当前观点交给下一观点 | 当前对象缩小/侧移保留上下文，下一对象接管阅读区；需要总结时重新归组 | T01、T02；文字、外壳、圆角作为同一对象协调。上下左右都可变，不能只缩外壳、不处理文字 |
| 一个概念展开为若干任务 | 先认清整体，再展开实际子项；处理/选中发生后收束结果 | 99-02、99-20；保留建立→展开→判断→收束，不继承三项/六项配额、固定列数或旧文案 |
| 比较与逐项讲解 | 共同条件保持一致，当前项突出，旧项退后，比较对象身份仍可辨认 | 95 row12、T05；变化发生在主次与证据，不能把比较机械画成上下游流程 |
| 给主体补充解释 | 主体保留身份并让出空间，新信息进入；解释完按需要回中或接走 | 99-09、T02；先测真实内容的空间，不为了配旁注无限缩小主体 |
| 从设备看清内容 | 内容从同一屏幕区域放大成为主体，外壳让位，媒体时钟保持连续 | 99-13、T10；绑定真实屏幕框和播放时间，不突然重播或换一张近似截图 |
| 从材料得出判断 | 材料保持身份，黑白蒙版/失焦让其退后，结论在前景读清；再决定返回或交出 | 95 row04、99-21、T07；背景、蒙版、前景独立，模糊不能作用到重点和品牌 |
| 输入、回答与持续阅读 | 输入过程可逐字；完整判断可刷出；补充词可淡入退下；对话组可上卷为新回复让位 | 95 row30、W01–W05；选择依据是文字职责，字幕仍是独立层，不要求每句换一种效果 |

“建立→变化→阅读→交接”是思考问题的方式，不要求每段完整演一遍；上游已建立就直接承接，结论可停在一句大字，稳定阅读不需持续漂移。

### 动作与镜头的共同约束

- 进入要让对象及时可辨认，移动和缩放要有目的地，落定后给足阅读。退出的任务是清楚交出注意力；入场和退出分别按建立与交接职责选动作，不默认完全镜像；当前指定原版轨迹优先。
- 同一运动组保持速度感和完成顺序协调；强调、载体搬移、文字揭示可用不同缓动。不要为“风格一致”把所有动作换成同一个spring，也不保留无理由弹跳。
- 一次变化有主要阅读焦点。旧项尚未退出、新项进入可以重叠，但两段主文字不能意外争抢同一区域。不能用单张终态图证明没有叠字。同级白字检查每项首个可读帧，不能因默认样式或继承透明度让后一个意外变灰；有职责的逐字显隐仍可使用。
- 相机推近服务可辨内容，横移服务焦点交接，回全貌服务重新理解关系；阅读时停稳。不要用全程慢漂移填时长，也不强制相机永远不动。
- 用口播的实际词组确定触发与阅读窗；快动作不等于快闪，读不完就改分组/时序。已有声音需与动作同步，不能每个小变化都加声。
- 连续对象在相邻场景保留身份、几何与媒体时间；话题真正改变时直接切换也可成立。不要求所有边界都变形或刷屏。

## 4. 模块不是一张固定尺寸的图

同一模块至少拆清三种责任：**内容是什么、怎样承载、怎样随时间变化。**

- 内容：本期文字、真实媒体、对象/项目数量和关系；不能藏在组件内部旧常量里。
- 承载：黑白表面、字阶、间距、可读区域、适用字幕避让；让主题统一决定外观，不在每个场景手写一套近似阴影。
- 动作：进入、阅读、强调、退出及交接的状态与cue；移交新文本/媒体时保持该对象的连续性。

原子组件可组合成关系模块，再由本期场景把关系模块与录音、媒体、品牌、字幕接起来。总结不强制胶囊，流程不强制节点线，媒体不强制设备框。使用成熟完整模块仍是优先选项，不能为了抽象而拆坏其已成立的动作。

**画布利用与局部避让：** 正文的布局起点应给内容足够面积；不要把示意用的安全框当成不能跨越的硬边界，也不因右上角有角标就封掉整条顶部、因一条字幕就永久封掉整个底部。全屏媒体可铺满，关键文字与主体按角标实际占用、字幕当前cue的真实宽高及运动路径局部协调。字幕未出现时可使用相应空间，出现时重新检查。规范站示例里的边距只说明一种构图起点，不成为跨期固定比例；真正需要读的材料宁可展开、分阶段或聚焦，不因过宽预留把内容缩小。

**分辨率适配与内容适配分开：** 在1920逻辑画布上整体缩放到4K，可以保持几何；它不会自动处理更长的中文、多一个节点、竖图变横图、双行字幕。后者需要内容测量、布局重排或分阶段呈现，不能仅把整组缩小。

现有代码能力、真实props、固定条件与未完成项见[组件复用图谱](references/component-reuse-map.md)。文档中的设计分层是调用与后续抽象方向，不表示已经新增了一套统一React组件包。

## 5. 没有现成组件时怎么做

**新做可复用组件**（Fred 当次明确授权时）按[新做组件流程](references/new-component-workflow.md)执行：
1. 从需求数据定场景，写一句“观众要看懂的变化”；
2. 用 `component_kit.py` 建工程，只用 kit；
3. 用真实素材，所有内容做成 props；
4. 规则检查（lint）、逐帧检查图、长短文案测试；
5. 云端渲染后交 Fred 挑选，认可的条目用 `component_kit.py intake` 入库。

**本期单个原创场景**（不入库）：
1. 先用一句话定义观众要看懂的内容变化，按第 3 节的关系选构图与动作，不先画卡片网格。
2. 外观、曲线、字体、音效按第 2 节，直接从 `templates/component-kit/src/kit` 复制使用。选择相关的动作质量锚点。**只借动作关系、代码为本期重写，属于场景级定制（2026-10-13 Fred 同意），按二创记 `adapted`**，字段填法见[组件库交付门禁](references/library-delivery-gate.md#场景级定制怎么登记)；找不到任何来源动作的才记 original，需要 Fred 当次授权。不能给没借到动作的代码挂编号。
3. 在原有 `styleContract` 写本镜具体决定：surface、typography、geometry、motion、camera、mediaBehavior，例如谁退后、谁接管、如何读完。不能每镜都粘贴同一份“黑白简约”。
4. 用本期真实最长文字、素材和字幕做关键帧，覆盖建立、最拥挤的中间态、阅读终态与接缝。Fred 确认后，按既有流程内部看动态。
5. 对照锚点检查有效内容面积、字阶、表面层次、动作关系和阅读节奏。符合色彩不代表达到质量；技术 PASS 也不等于视觉通过。

把当前设计决定留在一份 Manifest 中，不新增一套设计审批或第二份逐段计划。只对真实影响的画面和交接复核；已有保护范围继续保留。

## 6. 看画面时实际检查什么

- 这句新增了什么可见信息或状态，观众能否跟上同一对象？
- 是否有可删除的眉题、小标签、装饰icon、细描边、线条和大面积紫色？
- 在实际观看大小下主文字能否读清；密集材料是否有清楚的阅读顺序，而非缩到“放得下”？
- 表面、文字、阴影与运动是否属于同一对象；中间态是否拉字、叠字、裁切或退场残留？
- 毛玻璃是否保留了有用上下文；重点和角标是否清楚；字幕实际出现窗口是否遮住关键前景？
- 前后段是否连续，稳定阅读是否足够；变化是否来自内容，而非为避免“单调”不断换效果？
- 是否只用了第 2 节的值：颜色、阴影、圆角、字体、字重、曲线、音效音量（新做组件用 `component_kit.py lint` 先查一遍）？
- 换成更长或更短的文案后，是否仍不溢出、不叠字，主文字仍然读得清？
- 和库里已有组件相比，是不是同一个动作只换了颜色或素材？

这些是实际观察问题，不是增加几个布尔值就能证明美观。

# 整期编排：把组件串成一条视频

组件做得好，不等于整期好看。114 期 v1（2026-10-12）组件本身被 Fred 认可，但 21 段里 19 段要返修，问题几乎都出在组件之间：录屏原样干播、慢推和定格凑时长、同一组件反复出现、紫框/黑框、段与段硬接。v2 按本文件的规则重做并先出关键帧后，第二轮只剩 6 段小改，第三轮只剩 1 段。

本文件管整期层面：做分段工程、给写画面代码的子任务写简报、出关键帧前、渲染前都要读。单个组件的写法看 [DESIGN.md](DESIGN.md) 和 [动效手法](references/motion-craft.md)。

**先看 [好坏成对样例](references/paired-examples.md)**：118 期同一句口播、同一份素材，做对和做错各长什么样（8 组对照图）。下面的规则大多能在那里找到对应画面。

## 0. 113、114 期为什么能做到 90–95 分

114 v2/v3、113 v1 是目前质量最高的两期（Fred 给 114 打 90–95 分；113 是同一套做法，录屏还没补齐，尚未打分）。2026-10-13 对照源码、简报和返修记录复盘，好在这几件事，新一期照做：

1. **先设计“这句话怎么被看懂”，再找代码。** 每段先写“观众要看懂的变化”，把它落实成具体对象的状态变化：谁出现、怎么变、变完留下什么、交给下一段什么。例：113 讲开源和闭源用一本菜谱——“厨房在别人那里”推近后厨，“按份付钱”点菜单出价签，“菜谱拿不到”推近锁住的菜谱；下一段同一本菜谱开锁、盖公开章、变成模型文件下载到自己机器。114 讲 ZIP 和 clone：同一个源头分出两份，ZIP 那根线断开，作者从 v1 更新到 v2，更新只沿 clone 的线传过去。反例是 114 v1：按关键词找“像的”组件，出现一拆多用了多合一、没有赢家却用胜负比较、只标菜单位置没解释 clone 机制（见该期 `qc/组件重选-v2.md`）。
2. **为本期内容先做组件，再做片。** Fred 在 114 点名的 T04e、T05h、T05i、T17c、T09l 都出自第三轮新做组件；其中 T04e、T05h、T05i、T09l 是按 114/113 口播专门做的（`components-wave3-20261012/qc/specs.json` 的 `note` 写着对应哪一段），T17c 是同批的通用文件树。Fred 在视觉库挑过，再进片子。所以进片子时内容、对象和动作已经对得上。做法见[新做组件流程](references/new-component-workflow.md#本期驱动先为这一期做组件)。
3. **场景为本期重写，复用深入到动作层。** 113 工程拷进了 50 个原版组件，场景一个都没直接 import，而是把需要的动作拆进本期小件；114 实际运行的组件也主要是本期适配版（如 `v2b-T05i-UnboxResult`）。原样串组件，每个组件都有自己的开场和收尾，会不断重置观众正在看的东西。底层（kit、字幕、角标、音效、坐标映射）照用。
4. **时序跟真实口播走。** 用 `cue(段, n)` 取本段第 n 句的真实起点：说到“下载”文件才变，说到“放到自己的机器”机器才进来。先到位（0.4–0.7 秒），再给阅读时间，再响应下一句。
5. **转场写进代码。** 一个对象持续换角色：113 推荐“租机器”的答案卡长成器灵字标再分成四步；114 下载下来的代码卡变成文件夹，再接到结论胶囊。工程上共享上一段的几何常量、绘制函数或末帧取值时间（114 S14 直接取 S13 末态继续变形）。
6. **长段靠一条动作链撑住。** 114 S15 约 31 秒：结论胶囊 → GitHub CLI → 长出钥匙 → 插进 Codex 卡 → 卡长成真实界面 → 验证码交到浏览器 → 已授权按钮变成钥匙头 → 解锁下载、上传、建仓库。为一段写几百行代码是合理的，不用先做成通用接口。
7. **质量是返修收出来的。** 114 v1 21 段 19 段返修；v2 关键帧两轮后剩 1 段；成片后又改了 3 处和全片音效。检查要具体到段号、秒数、证据图和改法。例：113 第三轮复检发现首尾帧吻合，但接缝后 0.1–0.3 秒仍有灰糊和溶解（`ep113-v1/qc/round3/report.md`）——这种只看首尾帧查不出来。
8. **一个人掌握全片，其他人拿具体简报。** 写代码分组并行可以，但主会话定全片交接表、看所有检查报告、做最终判断。单纯加 Agent 数量得不到这个效果。分组时每组只渲到自己的目录（如 `qc/self/A`），推前端的汇总目录只由主会话写；116 期一组清空了公共目录，删掉了别组的关键帧。

工程结构直接用 [整期骨架](templates/episode-skeleton/README.md)（时间轴、段外壳、交接几何、分块渲染、音频和 BGM、推前端都已写好）。骨架的 `src/components/episode-kit/` 带着 117–121 期沉淀的共享件（`ep.tsx`、`ckit.tsx` 在 119–121 期逐字节相同）（真实比例 `CodexBox`、黑胶囊 `BlackPill`、毛玻璃 `FrostFocus`/`FrostLayer`、章节头与五种章节过渡、大播放窗片段 `ClipWindow`、来源小字 `SourceTag` 等），Fred 挑过的毛病已经在里面修好；直接用，只换每期的常量，不要重画近似版。新一期的 `render/`、`tools/` 脚本**从骨架拷，不从上一期工程整拷**：上一期工程里常是修复前的旧拷贝，会重踩骨架已修好的坑（121 期从 120 拷，又遇到 AAC 拼接错位和 `.bgm.json` 不让覆盖）。场景写法、共享件可以参考上一期；确实拷了旧脚本时，先搜上一期编号（如 `grep -rn "ep117" render tools`）改掉远端目录名（118 期曾同步进 117 的目录并 `--delete`）。


## 1. 整期首版的顺序（不能跳）

1. **先有真实录音和字幕。** 没有最终录音时，只做到关键帧，不出整片。按语速估出来的时长会逼着画面用慢推、定格去补时间（114 v1 的 S17 就是“为了凑估算时长停顿偏长”）。
2. **逐段方向**：按现有流程走建议页和 `library_gate.py`，录屏段也要写清“怎么包装”（第 2 节），不能只写“播放录屏”。
   - **写代码前先填逐句动作表**（[简报模板](templates/episode-assembly-brief.md)的“逐句动作表”；整期简报范例见 [120 期简报](templates/examples/brief-ep120.md)，它是逐段写法，逐句表按模板展开）：每句写对象、变化、证据位置、观看焦点、交接对象，并过完表下的五条自查。先定“这一句让观众看见什么变化”，再选组件；不要先选组件再往里填字。
3. **段间交接表**（第 3 节）写进本期简报，写代码前定下来；几何写进骨架的 `src/components/handoff.ts`，两侧 import 同一个常量。
4. **关键帧进前端**：每段至少有首帧、末帧，以及每个交互状态停稳时的帧；带真实字幕条和角标。Fred 10-13 要求关键帧比停稳帧多约 1.5 倍：每个主要动作再补一张中间态（砸下途中、展开一半、交接变形途中），note 写明是哪个动作的中间态；人物动画 B-roll 每段只要 2–3 张。用骨架 `tools/stills.mjs`（`SCALE=1` 出全分辨率）和 `tools/push_keyframes.py`（按 `keyframes/plan/Sxx.json` 的说明推前端）。
5. **Fred 确认关键帧**。要关键帧还是直接出片，按 Fred 当次要求执行，不额外提醒；没有说明时先出关键帧。直接出片时，第 2–9 节的规则和自检照样执行。
6. **动态自检**：渲染预览分段（1080p 即可），跑 `motion_audit.py` 和 `readability_audit.py`（第 8 节），每条结果要么改掉，要么写明豁免理由。
7. 再推 4K60 正式渲染。

## 2. 录屏段怎么包装

录屏是证据，但不能整窗原样播。

- **一进来就能读**：画面里要读的字 ≥ 24px（1080 逻辑画布）。整窗缩进大窗时字只有约 10px，必须推近到正在发生的区域（常见 1.6–2.4 倍）。118 期 S04 就是这样：60 秒以后推近真实录屏的搜索下拉（约 2 倍），结论数字用窗内黑玻璃加大字；46–55 秒原版素材里没有对应画面，才重建示意切换器（见[成对样例](references/paired-examples.md)第 4、5 组）。第三方录屏原样整窗播放 20 秒是 118 期 Codex 试作最大的失分点。`readability_audit.py` 会把“连续 3 秒以上满屏都是小字”报成阻止项。
- **镜头跟着口播走**：讲到哪里推到哪里。每次移动约 0.6 秒到位，停稳读 0.85–1.65 秒，再走下一处。单次移动超过 1.4 秒就是“慢推”。
- **纯滚动不超过 2 秒**；第一帧就开始动，不先静止再慢慢滚。长页面先跳到要讲的位置，或用长图加镜头定位。
- **每 2–3 秒要有一次可见变化**：点击、输入、结果出现、组件接管、镜头换焦。没有新变化就加组件或剪短，不拉长画面。
- **交互要演出来**：
  - 点击：光标移过去、点击环、按钮状态变化，配 click 声；
  - 输入：对话框弹出，打字机跟口播打出，再点发送，配 typing 声；
  - 复制：地址整行用局部蒙版或阴影抬起指出，光标点右侧复制按钮，图标变勾“已复制”；
  - 等待：用 T09n 快进，或直接跳切，不原速播放等待过程。
- **优先调用已有录屏组件**：CAM01–05（3D 录屏运镜）、T09a（镜头跟光标）、T09d2（发任务后步骤依次完成）、interaction-codex-full（Codex 输入框浮起发送）、T08b（长页滚到重点）、T09l（复制地址交给 AI）、T09i（按条件选中一行）。
- 录屏只截口播讲到的那部分；不要把前一段对话带进来（114 v1 S16 开头误带入了 CLI 授权对话）。
- 平台风险照旧：Codex 输入框左下的“完全访问”用实心块遮住，“群聊/加群”和真实密钥不上屏。
- **画出来的 Codex 输入框照真实截图的比例**（118、119 期 Fred 10-14，原话：“框比较大，这儿也比较大……有点宽，有点扁，就跟正常的不是很像”）：一行字约 860–960 × 140–176，两行再加约 44；圆角约 30、字号 30（不超过 32）；底栏左边“+”，右边模型名、麦克风、黑色发送钮；“完全访问”不画。Codex 标识约 44 号，放在框左上方、和框左边对齐。不要再用 1100×210、1400×270 这种大扁框；超过 3 行时框里只显示最后几行，表现“往上滚”，不把框撑大。参考实现：118 期 `ep118-v1/src/components/ckit.tsx` 的 `CodexBox`。**框里的模型名照 Fred 当前真实截图填**，组件里写死的是旧期的值，不凭记忆填旧型号（Fred 指出过“已经没有 GPT 5.5 了”）。
- **案例挑能看见结果的**（118 期 Fred 嫌“复刻 Windows 计算器”不够吸引人）：优先有可见成品和硬数字的案例（如“4 分钟复刻 Obsidian 快速切换器”，作者自述的数字上屏要能看出出处），去 YouTube、GitHub、抖音找公开演示下载回来，素材授权按现有规则处理。第三方视频在画面左下加“来源：…”小字；没有原版界面录屏的部分画示意图，不冒充真实界面。换案例要连带改稿、只重配那一段（见 fred-voice-tts）。
- **先扫录屏里的凭证，再限定取用区间**（116 期）：Fred 的 Codex 复刻录屏中途有一条消息带 ssh 地址和密码，结尾露出服务器 IP。做法：先 1 秒一格抽帧把整段看一遍，记下凭证出现的区间；场景代码里所有取源时间的地方都经过一个函数（如 `srcAt()`）夹在安全区间内，任何一帧都不会解码到凭证；“完全访问”逐帧实心遮挡；渲染后再对该段所有关键帧和中间态逐张确认。报告和文件里都不抄写凭证本身。
- **商单录屏要看得出是在产品里**（124 期 Fred：“整个视频都看不出来是在豆包里面的无限画布里”“你不用担心左边出现其他项目的名字，这是 OK 的”）：默认保留产品识别——logo、侧栏、功能标题都露出来；只遮凭证和账号隐私（上一条），不为了画面干净去裁侧栏。每次进入产品，先给完整界面停一下，再推近到要讲的地方。产品 logo、功能名在全界面下太小（约 20px）时，第一次出现用 `Spotlight` 只压暗无关区域（产品主区域保持亮），在 logo 和功能标题下挂白色标签（如“豆包电脑版”“无限画布”）。同一种标注全片最多三四处，别每段都来一遍（见第 4 节）。
- **画布、白板、作品墙不要用拉远的全景录屏**（124 期 Fred：“只要展示无限画布的时候都很丑”）：缩到 2%–5% 时每张图只剩几十像素，四周大片空白，录屏又是 1080p，再放大就糊。做法：先在产品里把内容排整齐（同类同尺寸、等间距、接近 16:9），截一张高清截图（4K 视口）；镜头运动在 Remotion 里做，推近到某一区时换成同位置的原图，保证清楚。录屏只留真实操作（拖入、选模型、点按钮、生成）这类近景。
- **用户没录到的操作可以模拟，但要接得上真实录屏**（124 期“把照片丢进去这一段我没有录，你可以模拟”）：用真实录屏的静帧当底，模拟物（照片卡、光标）的落点对准真实界面元素的准确坐标（例如输入框里缩略图的位置），落定后无缝切回真实录屏继续播放。不重画产品界面，不做与真实画面对不上的假操作。
- **录屏取段挑完整、可读的状态**（124 期“不要有点击展开全部的部分”“用我划上去的片段，要不看不完整字体”）：输入框里的文字要能完整读到（选用户把文字滚回开头的那段，或文字全部可见的那一帧）；避开折叠的“展开全部”气泡、加载中、文字被截断的画面。没有现成的好状态时，就定在最好的那一帧推近，再用点击动作切走，不硬播到难看的状态。
- **背景录屏可以一直滚**（Fred 10-13，116 S02）：录屏只当背景、上面压着黑色半透明毛玻璃（约 45% 黑 + 背景模糊）和结论胶囊时，后面的录屏可以整段持续滚动，不受“纯滚动 ≤ 2 秒”限制；动态自检时用 `--allow` 豁免并写明理由。胶囊放画面正中（中心约 960, 470），不贴底。

## 3. 段与段之间：交接表

分段渲染再拼接，接缝最容易露馅。不要用淡入淡出、整屏左右平移、PPT 式划走。

- **上一段末帧 = 下一段首帧**：同一个对象、同一位置、同一尺寸，靠一个连续动作交给下一段。
- 写代码前，在本期简报里列出每个接缝的交接表：

  | 接缝 | 上一段末态 | 下一段首态 | 动作 | 音效 |
  |---|---|---|---|---|
  | S01→S02 | 第三个黑胶囊问题 | 黑幕中央开出圆角窗露出 B-roll | 胶囊放大铺满成黑幕 | woosh |

- 常用交接动作（按内容选，不套固定套餐）：胶囊放大成黑幕再开窗；卡片变形成浏览器窗口；页面压成一条线，再从线上展开；文件行抬起变成卡片；三张卡聚拢变成三个胶囊；前后景深交换（旧窗口后退缩小，新窗口从近处压上来）；输入框对输入框的匹配剪辑。更多见 [对象过渡](references/object-transitions.md)。
- 跨子任务的接缝（不同人写的两段）必须严格按交接表的状态，写清坐标和尺寸。
- **交接对象连画法一起共享，不只共享坐标**（116 期）：S08 末 / S09 首那张文件白卡，`handoff.ts` 只定了位置，两组各画各的，字号 44 对 36、图标位置也不同，接缝跳了一下。跨组交接的对象要导出一个绘制组件（如 `FileRowCard`），两侧都调用它；类别标签、章节胶囊这类反复出现的对象同理，字号和字体常量也放进 `handoff.ts`。
- 检查：渲染后看拼好的成片接缝前后各 0.5 秒的动态，不只比首尾两张静帧。

## 4. 全片组件去重

- **讲解结构类组件全片只出现一次**：路线图、方法卡、双身份卡、问答回答这类。后面再讲到同一结构时，换一种表达（大字胶囊、关键词卡、对应画面），不要让同一个组件重新入场。114 v1 的路线图出现了 5 次，Fred：“用过一次就换”“不想再看到这个”。
- 同一播放外壳、字幕、角标、连续录屏、同一画布的延续不算重复。
- 出关键帧前，把全片所有段用到的组件列成一张表，查重复。
- **呈现手法也要去重，不只看组件**（124 期 Fred：“1 分 26 和 1 分 39 都是同样的一套组件跟一套内容，看起来挺重复，而且跟最开始也挺重复”）：同一种运镜套路（例如“缩进产品截图 → 标注 logo → 推近某一区”），以及同一个画面状态（例如开头那块铺满的总览板），全片只完整用一次。后面再讲“全在一张画布上”这类同义的话，换一种演法：留在当前画面里拉远补满、在物料上画圈、色卡连线、把总览板拉远成画布上的一张卡、光标点开某一版等。Fred 点名要“回到开头那个画面”时可以回，但回来之后的走法要和开头不同。
- **章节页每期换着用**（124 期 Fred：“章节页记得换几个用，不要每次都用那几个，我组件库里有 20 个呢”）：骨架 `chap.tsx` 自带的五种（T12k/m/q/o/s）不是默认全套。选章节页前先看 [章节动画](references/fred-chapter-transitions.md) 的“各期已用”表，优先选最近两期没用过的，用完把本期编号补进表里。从库里复制组件时只把 `Frame` 底色改透明、压在段首约 2 秒，组件本身不重画。章节名要清楚可读 ≥ 0.8 秒，章节卡不能盖住字幕（字幕层在章节卡之上）。

## 5. 强调方式

- **不用紫色框，也尽量不用黑框。** 要指出页面上的某处时，优先用：
  - 局部蒙版：用 kit 的 `Spotlight` 把其余部分压暗（0.6），目标保持原亮度。**不用白蒙版加失焦**——114 S08 推荐句用了白色模糊蒙版，Fred：“最后有个蒙蒙模糊的蒙版，这很奇怪”；白蒙版加失焦只留给 DESIGN.md 的“材料 → 结论”让位；
  - 阴影抬起：目标区域浮起、加柔和阴影；
  - 毛刷高亮：从左向右刷过字下。
- **黑描边的节点方块也算黑框**（118 S09 Fred：“黑框这种组件很丑”）：讲“文字变成图”这类内容，不要自己画一排黑描边方块。直接用真实产物图（放在白卡里），用 `Spotlight` 按顺序逐个亮起节点，旁边标出清楚的节点名。
- 紫色只用于少量文字点缀（当前关键词），不做框、不铺底。
- **黑白毛玻璃要用，但别做成同一个套路**（118 期 Fred 原话：“现在全篇其实你比较少用……之前还是蛮喜欢的，但你现在是完全丢失掉了”）：
  - 次数不设上限，但同一个样子不要在相邻几处连用；变化来自这一句的内容：可以是一行字/胶囊，也可以放完整组件（卡片、被划掉的会员卡、浮起的产品卡），黑白交替，或者干脆不加蒙版（119 期 5–6 处连用同一套“毛玻璃 + 一行字”被嫌重复）。与 feedback-rules.md“毛玻璃的适用边界”、production-defaults.md 一致；
  - 白底画面不要压全屏黑玻璃，整屏会发灰（118 S08、S10、S11 第一版，主会话自查发现）。素材在窗口里时，黑玻璃只盖住这个窗口（按窗口位置和圆角裁切），字居中在窗口上；白底上的多张卡用白色磨砂（约 `rgba(255,255,255,0.55)` 加 18px 模糊）配黑字。只有素材铺满全屏时才用全屏黑玻璃；
  - 白磨砂上别叠超大的黑胶囊（118 S07 Fred：“这里大胶囊有点丑”）。需要胶囊就用正常大小，或者直接放大字、重点词用紫色或划线表达；
  - 毛玻璃背后的素材继续播放。参考实现：118 期 `src/components/glass.tsx`，119 期 `ep.tsx` 的 `FrostFocus` / `FrostLayer`。
- 胶囊、卡片和标签放在目标旁边，不挡住正在讲的内容。
- **装饰性、漂浮的小黑胶囊标签默认不用**（115 v1 审看有 4 段明确点名小胶囊“丑、单调”，并定为统一原则；125 期照此执行）：给关键词、卡片、划线配的小胶囊，改成直接在画布上排大字或数字（MiSans Heavy，分主次）、在真实素材上用 `Spotlight` 压暗再提亮、或者用图标。段落结论、引语这类关键句仍可用一枚正常大小的黑胶囊（上面“需要胶囊就用正常大小”、骨架的 `BlackPill`、[成对样例](references/paired-examples.md)里的结论胶囊照旧有效），这条只收窄装饰性小标签。
- **高亮要停到那句口播说完**（124 期 Fred：“31 秒这里 highlight 只 highlight 得很短，马上就闪过”）：`Spotlight`、毛刷这类强调的退出时间跟着它对应的那句口播，不跟着下一个镜头的入场提前退；至少停稳 1.5 秒。交付前在关键帧里专门抽查强调的中段和退出前一刻。
- **胶囊压在满版、复杂的画面上时先加蒙版**（124 期“一整套品牌设计的时候加个蒙版，现在这个胶囊放在上面不是很明显”）：背景是铺满的作品墙、拼贴、录屏时，关键句胶囊先压一层毛玻璃（`FrostFocus`）或压暗再出，不直接浮在花底上。
- **几项并列信息用一张卡逐行点亮**（124 期 S02 三排“原型 / 风格 / 品类”灰标签 + 黑胶囊被嫌“挺奇怪”）：别拆成几枚漂浮的小胶囊；做成一张白卡，标题一行，下面每行“项目名（小、灰）+ 内容（大字）”，说到哪行点亮哪行，其余行保持淡色。
- 段尾交接不能整页半透明发灰地溶解或失焦淡出：页面要么整张退后、沉出画面，要么由同一对象接走。

## 6. 排版底线（每张关键帧都查）

- 关键内容 y ≤ 900（1080 画布），给字幕条留位；左右至少 80px；避开右上角标区。
- 同组卡片同尺寸、顶对齐、等间距；左右对应的模块按中心对齐。
- 搜索框、输入框按内容宽度，不留大片空白；圆角统一。
- 整体构图居中，不偏一边留空。
- 推近特写后，要讲的内容必须完整显示在画内（114 v1 S15 推近后没显示完）。
- 结论胶囊“不是 A，而是 B”这类关键句：居中，背后加蒙版，不放在画面下方。
- 白色小胶囊并排排列显得单薄（114 S06 Fred：“三个白胶囊有点丑”），优先用黑胶囊或卡片。
- **大字单独停着也要有第二个变化，上下别同时塞两组信息**（119 S02 Fred：“3 秒到 7 秒……就只是两个字儿，下面也没什么变化”“6 秒到 8 秒……上面一个下面一个，比较混乱”）：一句大字停超过约 2 秒，就让它带出下一个对象（卡片展开、数字滚动、对象接走）；两组不同信息不要一上一下同时进场，先后交接。
- **能用真实画面或真实界面动作表达的，不用自绘示意动画代替**：停掉、取消、删除这类动作，用观众真见过的界面操作（订阅面板里点开关，“自动续费”变“已关闭”），不做卡通式的“停掉”（119 期“有一点幼稚”）；某人说话、某件事发生，有真实画面就用真实画面（可以静音），不用声波条之类的模拟动画代表（121 期“这个模拟的音频动画有点丑”）。只有确实找不到画面时才画示意，并标“示意”。
- **重点信息不要缩在角落**（118 S09 Fred：“把一些小的卡片放到一个不显眼的地方，不是很好看”）：问题在位置。结论胶囊别挤在右上角、别压在素材上，放画面正中，或紧贴所指对象的上下沿；字号 ≥48px。
- **卡片一张张加入时，每一步都居中**（118 S07 Fred：“没有对齐”）：每加一张，整组平滑重新居中；或者一开始就按最终张数排好位置。不要出现前两张偏左、右边空着的状态。
- **主体要够大、要居中，不要“上重下空”**（116 期第一版 S07、S09、S12、S17、S18 都犯过）：主体占 y 200–880，整组垂直中心约 470；三张以上缩略卡每张至少约 420×236；正文 ≥ 40px 更稳。关键帧检查时专门看下半屏是否空着。
- **一屏信息太密就改成镜头逐块推近**（116 S12 Fred：“有点太密了，可以通过镜头变化优化”）：一屏超过 4 块信息时，不平铺；所有内容放在同一张大画布上，先全景 0.6 秒，再每次约 0.6 秒推到一块、停稳 1–1.5 秒读完，其余在画外或压暗。
- **内部叫法不上屏**（116 S10 Fred：“不要出现 Library 复刻这种字眼，就是 Fred 组件”）：组件来源批次（Library 复刻、第几轮等）对观众统一叫“Fred 组件”；编号可以保留。

- **推近不截字，卡内留白够**：截图、榜单推近时，要读的那一列左右至少留 24px，宁可少推一点（120 期把“claude”截成“laude”）；卡片里的文字离边框至少 40px、行距留足；装饰元素（图标、皇冠、角标）不压在文字上；气泡和卡片左右内边距相等，装饰收在内边距里（121 期“前面有空格，后面没有”）。
- **大数字按实际字宽留位**：版本号、计数这类会翻动的粗体数字比 DESIGN.md 的拉丁字母估算（0.58em）宽，按最宽的那个值留槽，翻动全程不被容器裁掉（121 期版本号“没显示完”）。
- **一个媒体窗配说明文字（标题、要点胶囊）时，优先上下排，不挂右侧竖列**：窗口居中，标题胶囊在窗口上方居中，要点胶囊沿窗口下沿排一排、逐个加入时整排居中。“窗口 + 右侧一竖列（标题、胶囊、小卡）”Fred 评价“排版太丑”（121 期）。图片不要套在更大的白卡里偏放，直接铺满窗口，或让窗口按图片比例。
- **旁边的视觉对象（计数点、附属小窗等，不是说明文字）后出现时，主体先居中**：主窗口先居中占好画面，旁边的对象出现那一刻再约 0.6 秒让位；不要一开始就偏在一边、另一边空着等（121 期“可以先居中，后面七个的时候再往右挪”）。这是“卡片逐张加入每一步都居中”在“窗口 + 附属对象”上的同一条规则。
- **引语、观点用胶囊表达，不做“白卡一行行字加 ↓”**：几个人的说法、一条链路，用黑胶囊横向流程（A → B → C 逐个砸出）；“以前 / 现在”这类对照，用上一行灰字被划掉、下一行黑胶囊（121 期“有点丑”）。
- **对比卡同尺寸并排**：各自“小标题 → 大图标或画面 → 一行大字”，内边距一致（120 期“这里排版很丑”）。

## 8. 动态自检：motion_audit.py

静帧看不出“慢”。渲染预览分段后先跑：

```bash
python3 skills/fred-remotion-output/scripts/motion_audit.py --dir <分段目录> \
  --allow S02 --allow S11:2-9 --json <本期>/qc/motion-audit.json
```

- **阻止正式渲染的四种**：定格/干等（画面 3 秒以上不变）、缓慢漂移、单次运动过长（一次推近或移动超过 1.4 秒）、纯滚动过长（页面滚动超过 2 秒）。
- **只提醒的两种**：停留偏长（2–3 秒不变）、持续运动不停稳（连续动 3 秒以上没有停下来读）。逐条看一眼，合理就留着。
- 默认裁掉底部字幕区再比较；采样固定 10fps，阈值按这个采样率校准。
- 用 114 v1 校准过：Fred 指出慢的 S01、S02、S03、S04、S07、S09、S12、S13、S15、S16、S19、S21 都会报出来（S04 开头的滚动是提醒级）。也有误报：组件结尾的正常停留（如 S12 第 11–14 秒、S20 各段问答停稳）会报定格，Fred 认可的 S08、S18 会有提醒。所以这是待查清单，阻止级的每条要么改掉，要么写理由豁免。
- 结果是待查清单，不是结论。数字滚动、图表生长、B-roll 这类有意的连续动作可以豁免，但要用 `--allow` 写明段号和区间，并在本期简报里写一句理由。
- 未豁免的问题不为 0，不推 4K 正式渲染。
- 单个组件演示片结尾的停留（2–3 秒）是演示用的，查组件时用 `--max-hold 3.2`。
- **常见误报：多对象接力的组件动作**（116 期 11 处阻止级里 10 处是这类）：目录树逐层展开、缩略图逐张倒出、展示窗抽出、线展开成卡并逐字打出，会被算成“单次运动过长”。逐条看确认不是相机慢推后用 `--allow 段:区间` 豁免，理由写进 `qc/motion-audit-exemptions.md`。结尾“以上就是本期内容”后的停稳也豁免。
- **对整片跑也可以**（125 期直接出 4K，没有分段预览）：先把成片缩成 1080p 再跑。报出来的“单次运动过长”大多是发布会实拍本身在动（烧胎烟雾、0.2 倍慢放喷流、坡道行驶、悬停），逐条按时间换算到段号和口播句、抽帧看过后豁免。要找的是画出来的示意动画该动却没动：125 期“把气球吹满一松手，它是不是嗖一下就飞出去了”，气球几乎原地不动，只有喷流在动——**口播里的动作词（飞出去、松手、倒挂、落地）说到时画面必须当场发生**，否则就是没兑现。

## 8.1 字看不看得清：readability_audit.py

`motion_audit.py` 查的是动不动，查不出“画面一直在动，但字只有几像素”（118 期 Codex 试作 47–68 秒整窗播放第三方录屏，motion_audit 全部通过）。渲染预览后接着跑：

```bash
python3 skills/fred-remotion-output/scripts/readability_audit.py --dir <分段目录> --json <本期>/qc/readability-audit.json
```

用 macOS Vision 按 1 秒一帧识别文字框：一帧里文字框不少于 8 个、而高度 ≥24px 的框面积占全部文字面积不到 45%，算这一帧看不清；连续 3 秒以上为阻止级，2–3 秒为提醒级。注意量的是文字框高度（约为字号的 1.4 倍），所以检查通过不等于满足“要读的字 ≥24px”，那条仍要看图确认。一枚大胶囊压在满屏小字上，面积占比通常仍不够，照样会报。豁免用 `--allow 段:区间` 并写理由。阻止级不为 0，不推 4K。

- **报出来先问：这几秒观众需要读界面里的字吗？** 需要读，就推近或重建（[成对样例](references/paired-examples.md)第 5 组）。不需要读、画面只表现“有这样一个工具在运行”，而结论已经由足够大的胶囊或卡片给出（例如 118 成片 87–92 秒：大窗播第三方截图工具演示，上面压“拆的是开源截图工具 ShareX”胶囊），可以豁免，理由写进 `qc/readability-exemptions.md`。这种整窗播放全片要少用、尽量短。
- 已知局限：1 秒一帧采样，只出现 1 秒的看不清画面不报；可读面积占比在 0.45–0.6 的半可读终端画面可能漏报；虚化背景里的字也会算成小字。只能在 macOS 上跑（用 Vision 和 swiftc）。

## 9. 出关键帧前的自检清单

按 Fred 历期意见（114 期起陆续补充）逐段查。Sonnet 逐张检查关键帧并列出问题，Opus 判断怎么改：

1. **录屏**：有没有整窗干播、慢推、纯滚动超过 2 秒、定格凑时长？
2. **交互**：讲到点击、输入、复制、下载时，画面里有没有光标、打字、状态变化？
3. **重复**：这个组件前面用过吗？讲解结构类组件是不是第二次出现？
4. **强调**：有没有紫框、黑框（包括黑描边节点方块）？能不能改成局部蒙版、阴影或毛刷？毛玻璃是不是总用同一种“一行字/胶囊”、黑白有没有变化？白底上有没有压全屏黑玻璃？白磨砂上有没有叠超大胶囊？
5. **排版**：对齐、居中、y ≤ 900、有没有出画、推近后内容是否完整（字没被截、翻动的数字没被裁）？重点胶囊和标签是不是缩在角落？卡片逐张加入、窗口旁对象后出现时，每一步是否居中？媒体窗的说明是不是挂成了右侧一竖列？卡片、气泡左右内边距是否相等？画出来的 Codex 输入框是不是真实比例、模型名是不是当前的？
6. **数量上屏**：口播提到数量（“几百万个”“900 多个”），画面就给出真实数字，取自截图原文，用大字或黑胶囊放在数字原位（114 S07 Fred 补的意见：搜 AI 约 700 万、video cutter 983、speech to text 约 9.4 万）。
7. **组件高潮不被截掉**：时间不够时，压缩或加速前面的录屏，保住组件最后的结果动作（114 S18 的文件过滤少了“3 个文件传进去”约 2 秒，Fred 要求完整呈现）。
8. **一次性码也遮**：设备验证码、一次性登录码即使已失效也打码（114 S15 露出过）。
9. **口播对应**：口播里提到的每个名词（工具名、按钮、搜索词、文件名），画面上有没有出现？比如“想录音就搜 speech to text”就要真的搜出来；讲到某个界面元素时，要用蒙版或阴影指出它在哪（例如 114 期讲 Star 时指出位置，再斜杠划掉“只是参考”）。
10. **真实画面优先**：有没有用自绘示意（声波条、卡通动作）代替本来找得到的真实画面或真实界面操作？上屏的真人是不是新闻当事人、演示自己工具的作者或画面远处的非主体，有没有无关的博主、采访、广告演员、店员？

- **场景多时可以分给几个最强模型的分身并行写**（119 期 11 段：主会话写开头两个文件，两个分身各写一个场景文件）：共享组件文件（119 的 `src/components/ep.tsx`）只由主会话改，分身只改自己的场景文件，需要新共享件时报给主会话加；改意见时用 SendMessage 续用原分身，保留它的上下文。

- **三组分身并行的做法**（120、121 期都按此做，10 段分 A/B/C 三个分身，各约 20–30 分钟写完）：主会话先写好本期共享件（章节表与章节过渡、视频窗、来源小字等，放 `src/components/` 一个文件）和整期简报 `qc/brief-v1.md`（分段方案、交接表、素材清单与可用区间、全片规则），再派分身。有左上章节标题常驻的期，跨组接缝可以用最省事的状态：**白底 + 左上章节标题常驻态**，两侧都只留这一个对象；组内接缝仍按第 3 节让对象持续换角色。素材还在准备时，分身先写不依赖素材的部分（章节过渡、数据卡、示意重建），素材到了主会话在简报末尾追加“素材已到”一节并通知。改稿重配音后只要段落和每段字幕条数不变，`cue()` 写法的场景自动跟上，通知分身改口播对应的上屏文字即可。
- **六组并行、只出关键帧、直接上云渲 4K**（125 期，正文约 4.8 分钟、9 段加过渡，Fred 要求“多用几个子 agent”“不用 1080p 视频，修好直接推云端”）：
  - 主会话写简报、共享件、交接几何，派 6 个最强模型分身，各管 1–2 段。主会话把每组关键帧拼成联系表逐张看，具体到段号、秒数和像素尺寸打回修改；125 期 6 组共返修 6 轮，主要是字太小、版面偏上下半屏空、示意图不够精致。
  - 看联系表时注意缩放：关键帧常按 `SCALE=0.5` 出图，联系表又缩一次，字看着小不一定真小。打回前按 1920 画布换算实际 px 再判断（125 期 B 组多数字号其实已达标）。
  - **哪组定稿先渲哪组**：用 `plan.py <还没好的段…>` 跳过未完成的段，`cloud.sh go` 先渲已定稿的；后面的段好了，同步 stage 后用 `cloud.sh chunk <台> <段> <起> <止>` 按块分到各台补渲，已拉回的块会跳过。125 期第一轮 33 块渲完时，最后一组还在改。

  - 返修只重渲受影响的块：旧块挪到 `out/chunks-old/`，`cloud.sh chunk` 补渲；音效变了就先重渲 `out/full-sfx.wav`，再 `REUSE_SFX=1 python3 render/final.py`，最后跑 `loudness.py --fix`（125 期 -10.2 → -9.6 LUFS）。

## 12. 交付前检查

1. **画面**：总帧数 = `timing.json` 的 `totalFrames`，3840×2160、60/1。
2. **音频流程**：音效轨（`noVoice`）和口播轨分开渲，混音后过 `alimiter`，再用 `bgm.py` 加 BGM。骨架的 `render/final.py` 已按这个顺序写好。
3. **BGM**：从 0 秒到结尾都有；固定过渡插入段照常有 BGM（纯人声不让位），封底等自带音乐的区间按 `bgm-plan.json` 让位；音乐不够长时的拼接点要人耳试听，没听过就写“接缝待试听”。
4. **响度**：AAC 实测真峰值 ≤ -1 dBTP（114 v3：-9.6 LUFS、-1.3 dBTP）。

7. **字幕、角标**：字幕和口播同步；角标显隐按第 7 节，接缝两侧一致。
8. **平台安全**：“完全访问”、密钥、一次性码、“群聊/加群”。

## 一句话总结差距

右边是“这句话配一个组件”或“这句话配一段相关素材”；左边是“**这句话让观众看见哪个对象怎么变**”，再用组件动作和素材把这个变化演出来。技术检查两边都通过了，差距全在这一层。

## 1. 开场第一秒：真实页面打底、数字落到原位 vs 白底计数器（`pair-4s.jpg`，左为 v3 返修后）

口播：“这个 GitHub 上有一个开源项目，一周就涨了十三万颗星。”

- **好**：第 0 帧就有内容：周榜页铺底、压暗磨砂，正中星标数字从 0 滚到 `+130,471`；磨砂散开后，数字飞落到 REA 那一行旁边，那一行抬起。观众看到：这是哪个页面、哪一个项目、精确涨了多少。
- **差**：白底上一个大计数器从 0 数到“130,000”，没有页面、没有出处，数字也不是原文。
- **改法**：大数字开场本身没错（6.1 节推荐的就是这种），差别在于有没有真实页面打底、数字是不是截图原文、最后有没有落回它在原画面里的位置（episode-assembly 6.1、第 9 节第 6 条“数量上屏”）。

## 2. 五个项目一览：可比较的信息 vs 只有名字（`pair-8s.jpg`）

口播：“挑了五个我觉得最值得看的项目。”

- **好**：五张 logo 卡一排居中，每张带本周涨星数，下面一枚黑胶囊“本周最值得看的 5 个”。观众能直接比较五个项目谁涨得多。
- **差**：五张卡排成 3+2，卡里只有名字、一行副标题和编号，没有可以比较的信息；两排排法也让画面重心不稳。
- **改法**：同组卡片一排居中；卡里放能比较的信息（这里是涨星数），不只是名字（episode-assembly 第 6 节）。

## 3. 构图居中：主体在中间 vs 整组偏右（`pair-40s.jpg`）

口播：“现在装上 REA……”

- **好**：REA 图标在画面正中，接下来插进 Codex、Claude Code。
- **差**：钥匙和两张灰色锁卡整组偏在画面右侧，左边大片空白。
- **改法**：主体先居中；旁边的对象出现时再让位（episode-assembly 第 6 节“整体构图居中”“主体先居中”）。

## 4. 没有原版录屏时：重建示意 vs 播一段相关视频（`pair-51s.jpg`，左为 v3 返修后）

口播：“比如有人拿 Obsidian 做了个测试，你按 Command 加 O，输几个字母……”

- **好**：没有 Obsidian 原版界面录屏，就用 kit 画出“Obsidian 卡 + ⌘ O 两枚键帽”，按口播逐个按下，后面再接示意切换器。画出来的部分不冒充真实界面。
- **差**：整窗播放第三方作者的录屏，口播说到“⌘+O”时画面上根本找不到。
- **改法**：口播里的每个名词和动作，画面上都要看得到（第 9 节第 9 条）；手头的素材没拍到这个动作，就重建示意，不是随便放一段“相关的”视频。参考源码：`templates/examples/scene-ep118-ReaCases-footage-rebuild.tsx` 的 S04 前半段。

## 5. 录屏要看得清：推近到正在发生的地方 vs 整窗播放（`pair-60s.jpg`，左为 v3 返修后）——差距最大的一处

口播：“然后还照着做了一个网页版……然后拿四千九百多次搜索跟原版对比。”

- **好**：播的是同一段真实录屏，但镜头推到复刻页的搜索下拉（源画面 800×330 的区域放大约 2 倍，列表字约 30px），口播说到哪就看哪；“4,915 次搜索 · 和原版对比 / 一条都不差”用黑玻璃压在继续播放的录屏窗上，大字居中。来源小字放在左下。
- **差**：约 47–68 秒共 20 秒，同一批第三方录屏整窗播放，界面字只有几个像素，看不出在演示什么。技术检查和 `motion_audit` 都没拦住（画面一直在动，不算定格也不算慢推）。
- **改法**：录屏里要读的字 ≥24px（第 2 节第一条）。**先推近**到正在发生的区域（1.6–2.4 倍）；原版素材里没有这个状态，才重建示意（第 4 组）；结论数字用窗内黑玻璃加大字。参考源码：`templates/examples/scene-ep118-ReaCases-footage-rebuild.tsx` 的 `vRev`、`OBS_DROP`。渲染后跑 `scripts/readability_audit.py`，它会报出“连续 3 秒以上满屏小字”。

## 6. 第三方演示：结论放大 vs 原样放映（`pair-93s.jpg`）

口播：“截图、标注、换背景、加阴影全都有。”

- **好**：演示画面压暗模糊做背景，四枚结论胶囊“截图 / 标注 / 换背景 / 加阴影”按口播逐个打勾。观众不需要看清原界面。
- **差**：演示界面整窗播放，右上加一个小勾选框“The beautifier”，界面里的字看不清，口播列举的四个功能在画面上对不上。
- **改法**：口播在列举功能时，画面列出这几项并逐个点亮；原素材退为背景（毛玻璃上放完整组件，第 5 节）。

## 7. Codex 输入框：真实比例 vs 自己乱画（`pair-99s.jpg`，左为 v3 返修后）

口播：“你复制发给 Codex，它就帮你装好、连好。”

- **好**：真实比例的 Codex 输入框（Codex 标识在左上、底栏有模型名和发送钮），安装命令粘贴进去后发送。
- **差**：一个黑色终端框和一个空白输入框叠在一起，“Codex”字被压在框下面，光标停在发送钮上。
- **改法**：直接用骨架里的 `src/components/episode-kit/ckit.tsx` 的 `CodexBox`，不要重画（第 2 节“画出来的 Codex 输入框照真实截图的比例”）。

## 8. 段尾总结：用前面的对象收 vs 把旁白再写一遍（`pair-109s.jpg`）

口播：“所以 REA 最大的价值不是照抄，而是看到一个好用的功能，让 AI 搞清楚怎么做，再变成你自己的。”

- **好**：三步链“看到好用的功能 → AI 搞清怎么做 → 变成你自己的”，用的是前面出现过的软件卡、源码卡，按口播逐步点亮。这是结论在解释关系，而且回收了前文的对象。
- **差**：一张模糊卡上写“变成你自己的功能 / 理解实现 → 按你的需要重做”，就是把字幕又写了一遍。
- **改法**：总结要把本段前面建立过的对象再拿出来，演出它们之间的关系；只把旁白换个字号写出来不算总结（第 0 节第 5、6 条）。

# 从稿件到稳定质量的制作默认值

新一期由助手先给逐段图文建议，Fred修改并选方向；优先展示准确组件截图/片段，必要处再生分镜图。随后用真实组件出关键帧，Fred提意见并确认后，助手内部检查动态、声音与接缝，再出完整视频。详见[路线与确认](references/route-and-storyboard-review.md)。总结句可按内容评估黑/白毛玻璃，不要求每段使用。

拆稿/规划时读一次，用于把本期稿件接到现有资产、媒体与动作规则；不另建Manifest或固定模板。之后只取当前场景小抄。

接手初检先核对四个实际输入：当前稿/WAV/SRT及处理状态、真实媒体与缺失录屏、当前前端的版本和真实意见、已选组件/分镜及其准确来源。已加速/加增益的音频不得重复处理；缺录屏只保留明确占位，不伪造产品UI；有准确库方案先看其实际动作，不退成一套灰底文字页。检查结果补同一Manifest的输入和待补项，已有有效检查按hash复用；“直接渲染”按当次授权缩短创意往返，不伪造已看样片或PASS，不把本期直出变成永久跳检默认。

Fred新一期完整视频先核对[固定过渡配音](references/fixed-skill-library-insert.md)是否已含，并在规划阶段安排一次；不用让Fred重复录制。只固定音频，当期动画单独提供／指定，缺少时标待提供，不自动使用109期旧动画。不同解释任务分别选择真实证据与动作关系，建议前运行[整期分配检查](references/component-distribution.md)，避免单镜头都过关但整期不断重复同一个结论模块。

## 先做六个相连的决定

1. **本句责任**：观众此刻要认清什么，动作发生后理解什么。读取全文稿及真实录音，锁定原话、源音轨和帧率；总述、实操、精读、比较、结论分别安排。
2. **内容证据**：哪张原图、哪段录屏或产品实拍承担信息，哪些是解释动画。先查用户指定素材，再按内容挑库；示例UI和库中旧文案不成为本期事实。
3. **载体与构图**：根据横竖比例、可读区域和设备身份选全屏、浏览器框、电脑、手机、iPad或图卡。内容、外框、前景文字、角标分别管理；同组字体与视觉大小一致。
   后续16:9录屏/实拍/生成视频作为主内容全屏播放时，直接复用[默认大播放窗口](references/fullscreen-video-window.md)及其真实模板：4K窗口3600×2027.11、居中、圆角48、阴影`0 32px 50px #0002`、无描边。1080逻辑舞台由父层放大时使用半值；不为字幕缩小整窗。此默认来自2026-10-04当前明确跨期要求，其他用途和当次覆盖独立处理。
4. **动作与时钟**：写清当前状态、必要变化、阅读停留与交接；已有上游建立或静态阅读无需硬加动作。库的完整组件负责成熟的动作关系，T索引负责局部交接，W索引负责文字形式；时间重新绑定本期口播。
5. **声音与品牌**：关键动作主动选声，静音也有理由；数字滚动声只配数字滚动。FredTalk横版解释动画使用已有角标规范，录屏/实拍作为主内容播放时关闭新增右上角角标，Fred 人物 B-roll 动画全屏播放时加角标（版本按 corner-branding 核对），混合场景按播放区间切换；公开评论区的昵称头像不用打码，“群聊/加群”仍不上屏；需要烧录字幕时按[横版得意黑模块](references/landscape-subtitles.md)叠加并为胶囊/卡片等关键前景留位；保留实际音轨与混音。
6. **连续出口**：下一段从当前尾态接走什么，前景何时退出，媒体时钟是否继续。不要把每段都做成一次重新开场。分段制作时，写代码前在本期简报列出[段间交接表](references/episode-assembly.md#3-段与段之间交接表)。

以上放进已有`visualPlan`、`motionEvents`、`referenceChoices`和`sceneGuide.applications`，不增加独立的计划表。新设计主要改本期内容、素材、cue及必要几何；可直接复用完整优秀模块，也允许新方案。

## 少返工的执行顺序

### 将要求落实到当前执行包

详细制作要求不应只留在聊天、某个子任务提示词或生图 Prompt 中。接手和每轮反馈时，把本次仍有效的全片决定写入现有 `designContract`（可用 `currentRequirements` 保存来源、适用范围、决定和可观察检查），单镜决定写入原 `visualPlan/motionEvents/sceneGuide.applications`。分清：明确固定项、按内容选择的方式、已经成立的保护范围、当次交付边界。用户举例的“大主体缩小让位”是可选关系，不能覆盖其同时提出的并行、局部放大、归组等方式。

`scene.py --manifest ... --scene-id ...` 会携带整片 `designContract/fonts`、当前场景和相邻交接、字幕窗口及品牌设置。实现者先核对实际包，而不是假设长对话已传到；有委派时把同一包和准确参考区间交给执行者，主线程仍检查合起来的效果。根合同缺失则从当前已知要求补齐，不自行编造用户批准。相关文字组把指定字体/字重、同职责色彩、对齐关系和首个可读状态带入；字幕把产品名称和指定称谓带入；混合媒体镜头把角标关闭区间带入。后续指定的准确参考字体优先于中途尝试的字重方案，留白仍需保住。

一段动作要能指出以下关系，沿现有字段记录，不增加一份逐镜表：

- **内容对象**：这句看哪份文件、哪个界面、哪组文字；沿用哪个上游对象。
- **文字变化**：原文/节选/结论各承担什么职责，何时输入、逐项突出、替换或退出；“有字”不等于“文字有表达变化”。
- **对象与镜头变化**：什么在移动/展开/归组，观看焦点何时从哪里转到哪里；相机与对象移动分开判断。
- **阅读与交接**：真正要读的内容是否到达可读尺度、何时停稳，下一句接走什么；无变化的稳定阅读要有具体阅读对象。

不要求每句都有上述全部动作；纯结论、稳定阅读可以简单。同一句通用说明复制到所有规则，不算落实：角标检查应指向位置/可见轮廓/运动避让，文字检查应指向实际最长内容，媒体检查应指向真实播放与 ROI。`scene.py` 对完全相同的规则决定给出提示，仍由助手判断，不能靠同义改写消除问题。

改过方向后，同轮核对 `visualPlan`、`motionEvents`、关键帧标签/目的、实际源码调用和前端版本，退役旧描述。历史批注保留在历史记录，不能让旧“窗口进场”继续与新“透明 Logo”并排作为当前动作。记录只能按实际实现与检查更新，不把所有 `planned` 批量改成已完成。

### 3D录屏运镜的内容职责

3D用于让平面内容的位置、层次和操作关系更直观。先按真实口播和素材确定信息推进，再选镜头路线、透视、滚动、停留及成组突出；每次移动要有明确的信息落点。阅读处停稳、路过处连续通过，速度按距离与内容分配；认可案例不固定新片的角度/次数/时长。执行与审看见[按实际内容编排3D运镜](references/screen-camera-selected.md#按实际内容编排3d运镜)，沿现有visualPlan/motionEvents记录，不新增审批或自动镜头生成能力。

### 按认可维度保护基线

先把用户所指预览/hash对应到实际调用的源码，再从原话分清镜头路径、源滚动、停顿、突出、内容、构图与声音中哪些成立、哪些待改；沿原修订清单记录认可范围，不把一句局部好评登记成整段批准。用户要求结合两版优点时，分别绑定各自准确来源。

修改高亮、蒙版、留白或文字时，保留已经成立的多目标换焦、运动曲线与源时钟，不顺手换成另一条简单推拉。新增停留确需调整时序时，只改目标阅读窗口及必要的相邻连续性；用同一内容阶段的基线与新版正常速度对照，确认保留项没有退化。新内容可重新编排路线，旧案例的认可不代替本期验收。

### 在扩展全片前检验表达和质感

先从本期实际风险选代表段，使用真实最长文字、真实录屏、字幕/角标和相邻交接。用已认可参考的同职责阶段与当前关键状态、正常速度短段对照：主内容面积、字阶、表面与阴影、动作顺序、镜头焦点、阅读停留、出口分别看。某种新布局明显比参考粗糙，就先修这一类再扩展；不能以“更多组件”或“更多帧”代替同等质量。

全片再看各段信息怎样推进：是否所有操作都被盖成同样一句字，是否每句都清空重开，是否只换皮却重复同一动作。比较关系决定并行/同尺度对照，精读决定局部靠近，过程决定同对象接力，结论可直接稳定呈现。多样性按内容选择，不规定某种镜头必须出现几次，也不把有效胶囊、蒙版或设备全面禁用。

审看范围从当前前端完整行清单及 Manifest 获取，包含没有备注的行；代表帧/章节摘要不冒充全量。用户只要关键帧时停在该范围；允许整片时，内部正常速度检查每个完整语义段和接缝，最终连续播放。已有确认与当次直做授权按原流程生效，不把诊断任务再次交回用户逐帧审批。

### 把返工经验用于判断

#### 将“流畅、跟口播”落实到可观察状态

先在现有 `motionEvents` 写清建立、变化、完整可读、保持和交接的实际 cue；只列本镜真正需要的状态，不增加固定时长或一份新审批表。

| 触发情况 | 实现与检查 |
| --- | --- |
| 一段连续移动在多个锚点反复停顿 | 区分“路过点”与有目的的停靠点。路过点保持位置连续及速度方向协调；不要每个分段都重启 ease-in-out。需要停下阅读时明确保持区间，不能全局改成匀速。正常速度看完整轨迹，并在锚点两侧检查实际生产状态或帧 |
| 胶囊先动或变高，内部却空着 | 定义首个可读状态。文字应与它需要的空间一起就绪；若先建立带首行的长胶囊，补充 cue 到来后同步扩高和揭示下一行。允许短暂、有职责的空壳展开，但不能把等字的空区域当阅读停留 |
| 枚举项太快读不完，或提前全摆完 | 入场、强调、阅读、退出分别绑定当前录音的词组，量测从完整可读到退出的真实窗口。必要时前提入场，但不能抢走上一句焦点；总述与分述不同，不按对象数量等分段长 |
| 九宫格变成逐页快切 | 按实际口播选格、合格、删格，先形成同对象动作链再实现；格数不等于成片镜头数。详见[多状态复刻](references/chatgpt-pro-storyboard-replication.md#把九宫格变成按口播推进的动画) |
| 对象连续但入场、开窗或连线拖完整句 | 分开动作完成与阅读窗口，对照已认可组件的同职责动作，缩短无信息行程后停稳。长口播按新的语义推进，不用慢箭头或脉冲撑时间，不固定统一动作秒数 |
| 连接线之前先冒出小点，箭头方向或落点怪 | 核对进度零、第一可见帧和目标就绪；零长度不渲染有圆端帽的路径或游走点。线、头、端点同一进度控制，箭头尺度/切线/锚点按真实两对象边界检查；无关系职责时不用箭头 |
| 左右模块外框居中却看着不齐 | 以当前可见组的文字、标题、图标、胶囊和对应底行量测视觉中心与基线，检查运动中间态；不只对齐外框，也不强迫语义不同的对象机械等高 |
| 同一黑窗或卡片换内容时闪一下 | 继承同一外壳、锚点、尺寸与层级，文字层独立交接。核对是否重复叠加全场 wipe、旧场 Freeze、组件入场或隐藏条件；选一个有语义的接管路径，不把整层消失当文字替换。话题真实改变时仍可直接切换 |
| 版式已成立，但讲解多项时没有焦点变化 | 保留排布，按口播只突出当前项，再恢复或交给下一项；可选轻微靠近、变暗/蒙版或清晰度差异，不为“有动态”乱移整组。长阅读与最终结论允许停稳 |
| 结论先说，原因后到 | 先给结论完整的阅读位置；需要腾出原因位置时，让同一结论平滑让位；已有可读空间时可原位保持，再按 cue 建立原因。居中、右移只是可选方向，不固定复制到所有因果段 |

检查实际第一可读帧、扩容/换词中段、最大相交态和交接两侧；同时检查最长文字、字幕与角标。最终静态排版好看、曲线源码连续、文件能解码各有检查范围，不能互相替代。正常速度检查范围与当前用户授权一致；用户指定自己看或直出时保留未审看状态，不追加样片审批。

先区分本次明确固定项、可覆盖的默认值、场景条件和历史失败症状。固定项按当前原话执行；其余按本句责任选择，不把单期秒数、白底、居中、设备型号、并发数或组件数量提升为全局要求。胶囊、纯文字、稳定画面、不对称构图都可以成立；有意的简洁与阅读停留不需要为过检查增加装饰或动作。

反馈说“单调”时，先判断缺的是过程、重点、阅读内容还是镜头关系；说“丑”时，先对照尺度、字阶、构图和运动，必要时重新选型，而非继续给失败布局叠动效。优先内部修掉重叠、难读、无意义空场与突兀冻结，按已有授权推进；不增加每轮都要用户确认的环节。具体比较方法见[内部审看](references/content-to-component.md#两个问题都通过才算内部审看通过)。

默认先把实际素材、最长文字、适用字幕/角标和关键交接做成真实关键帧供Fred审看，确认后内部检查短动画，再扩到整片输出；有限返修及当前明确省略审看时遵循本轮范围。现有授权范围内直接推进，只有影响内容正确性、素材选择或交付范围且无法判断时才问。

反馈识别、局部修订、前端回填和合并交付统一按[渲染与交付](references/render-and-delivery.md)执行；当前有效版本、用户意见与实际输出身份必须一致。用户明确要求直出时按已有授权推进，如实记录检查范围。

## 组件适配信息随当前场景执行

同组件同职责时复用共享字体/排版配置；按背景、操作、结果分配载体，完整原文和逐项强调共用布局，媒体转总结继承真实末态。对应做法分别在 typography、content-to-component、text-presentation、media-and-overlays 维护，不把单期字号、三行、紫色或组件顺序设为跨期默认。

`scene.py --manifest ... --scene-id ...` 带出 `componentAdaptation`、本段 `readingPlan/preserveObjects` 及邻段已声明映射；实现前消费它们并绑定实际调用。检查是声明对照与针对本场景的提示，不是新的用户审批或美术自动判定。字段未使用的旧片不重规划；新适配示例见[复用图谱](references/component-reuse-map.md#共享适配工具)。

## 完整视频音乐职责

当前Manifest的audio.bgm按[背景音乐](references/background-music.md)记录，从实际声音用途确定muteRanges，不以全屏、源文件有音轨或组件名自动关BGM。正常讲解持续播放原音量；观众需听作品原声时BGM静音，音乐时钟继续。Fred本机私人依赖默认可用，他人自备音乐；不上传本机依赖，云片下载后本地合成。输入已有BGM时不重复添加，独立音频交付不默认扩展为混音。

# 横竖媒体、设备载体与毛玻璃前景

当场景使用`media-layout`、`device-frame`或`frosted-focus`时按对应小节读取。适用规则为F20、F06、F05；角标由`brand-corner`单独带入；录屏/实拍/生成视频作为主要观看内容播放时关闭新增右上角角标；Fred 人物 B-roll 全屏播放除外，保留角标（见 fred-remake `corner-branding.md` 108期补充）。全屏和窗口播放都适用，源素材自带标识保留。混合场景在原`brandCorner`记录显隐区间，解释动画沿用原有规范。

## 三层几何分开，动作相互关联

| 层 | 记录在本期已有计划中的决定 | 局部修改时保护什么 |
| --- | --- | --- |
| 原始内容 | 真实路径/hash、有效内容ROI、原生尺寸、入出点与帧率 | 内容身份、文字/产品细节、原比例、播放连续性 |
| 外框/设备 | 全屏/窗口/电脑/手机/iPad，真实屏幕bbox、内边距、圆角和缩放锚点 | 用户认可的载体、光学大小、动作与画面占比 |
| 前景与品牌 | 文字组、蒙版职责、角标独立层、字幕/关键UI安全区 | 字体/字重、层级、对齐、局部底色对比 |

新增记录写进原`visualPlan`与素材台账；这些是设计决定，不宣称已有自动适配API。只有源素材或画面职责改变时重新求几何，不因换一张图重做全部布局。

横版电脑/窗口通常更适合横向实操，竖版手机录屏可放手机或竖向内容框，iPad按实际画幅和内容职责选择。先验证真实素材比例；`contain`保全内容，`cover`只在允许且记录ROI的裁切时使用，不能拉伸或裁掉关键结果来填满设备。多对象比较按可见内容的光学大小与共同基线协调，不能只让透明PNG外框同宽。

入槽前先辨认源素材已经带有的设备边框或浏览器外壳，避免在黑框上再叠同样的黑框。需要嵌入真实设备时按有效屏幕框裁切内容，外壳与内容裁切同步；更换载体不改变真实UI的比例。

采用已有成片进入整片前，核对其内嵌字幕、角标、外框、旁白、BGM、源声/音效、原速度与尾部保持；在原素材/声音计划中明确每层保留还是由本期接管。不能把完成片当无声裸录屏，再重复叠字幕、角标或混音；需要完整源声时保留末句和尾音，声音处理沿[背景音乐](references/background-music.md)及当前音频职责执行，不默认去掉已有声音。

用户要求去边/全屏时，分开定位源素材内置边、外部容器留白和真实页面背景；网页白底不是排版白边。按有效内容等比作最小必要裁切，并在源页面滚动、缩放和关键结果阶段复查UI，不能仅验证一帧。用户指定设备或稳定播放时保留该选择，通过合理屏幕比例和薄框扩大内容，不强加持续推拉。

### 同类播放窗口的尺度

录屏/成片是当前主要观看内容时，先让实际内容占据足够大的可读区域，再安排外框和辅助文字。对照本期已满意的同职责播放段，统一稳定播放态的可见内容宽度、光学大小与重心；不能只统一PNG或DOM外框宽度，留下过厚设备边、页眉和黑色两侧空槽。多视频比较、缩略总览和讲解配图有各自职责，不强行使用主播放窗口尺寸。

媒体可以铺到字幕后方，字幕遮住无关背景或非关键底部可以成立；关键按钮、结果文字、人物表情和当前阅读区仍须可见。不要为字幕永久空出整条底部而把视频整体缩小。改尺寸时检查真实播放中的有效ROI、字幕出现窗口、载体入场/缩回和相邻出口；用户已保留的窗口表面、圆角和设备身份不随放大自动删除。2026-10-04 Fred进一步明确将108期v9大播放外壳作为后续全屏主视频默认：实际调用[FullscreenVideoWindow](references/fullscreen-video-window.md)，4K为3600×2027.11、圆角48、向下32/模糊50px黑色13.33%阴影，居中。多窗比较、设备内播放与解释动画仍按各自职责，不将此尺寸套到所有构图；当次明确要求优先。

窗口型品牌落版被选定时，画布底色、窗口表面、左上按钮、Logo与文字组分别记录；黑舞台＋白屏幕是可选对比，不是所有结尾的默认。保留官方Logo身份，必要时只处理透明边/白底，不重画标识；浅色承载面用清晰深字。整组以可见Logo轮廓与文字测视觉居中，去掉重复收尾小字，不能只把每行分别居中就认为组间关系成立。

## 播放速度独立于载体运动

先按口播划出连接/处理/结果等实际阶段，再安排每段入点、速度与停稳。内容浏览、流程总览可以加速；精读、证明操作和关键结果需要留可读时间。用户要求“完整播完”时映射目标首尾并包含最后内容，不能靠截断假装完成。

源帧率与时间单位明确；恒定速度可按`sourceTime = sourceIn + elapsed * rate`计算，分阶段速度连续衔接。帧范围半开/闭合遵循本期Manifest及渲染器约定；不得把秒数直接当帧号。镜头靠近、媒体在屏幕间交接、蒙版显隐都沿同一媒体时钟；放大后缩回仍是同一源文件、同一任务/弹窗与连续源时间，不能切到另一张近似界面。没有阅读或交接职责的推拉可直接去掉，让真实关闭/返回动作自然承接。画面加速不自动改变口播。

分别排查镜头变焦是否过慢、源操作是否被慢放、停帧是否有阅读目的；不能为凑段长统一拉慢或在无信息位置冻结。稳定阅读可以成立，要能指出此时在读什么、为何需要停留。优先调整素材入出点和操作分段，按本期口播检查实际速度；不规定统一倍率或最长静止秒数。

用户要求多个例片“都在播放”时，每个槽绑定实际视频和自己的源时间，不用poster、截图或固定首帧冒充播放。先比较源片与最终MP4同时间的实际状态，区分源片自带停顿/黑场、合成取帧异常和播放器卡顿。例片展示默认按自然速度选有内容推进的有效区间；循环只用于允许重复的展示素材，记录源首尾与接法并看回绕，不能把真实操作重复当作新的结果。四槽合成一个槽或跨场景交接时，媒体时钟独立于位置/尺寸插值，检查交接两侧源PTS；不因组件重新挂载把内容倒回开头。

真实操作与解释性聊天分清用途：示例聊天可采用熟悉的气泡、头像和消息顺序提高可信度，但不冒称实际客户记录。隐私遮挡沿用当前范围；用户撤销普通信息遮挡后核对相关层，真正凭据继续局部保护。播放映射或裁切改变后重查保护层覆盖，不用大面积遮罩掩盖内容。

“全屏”先结合现有画面解释：内容在认可载体内尽量填满，还是内容接管最终画布。用户已强调保留外框时直接保留；有实质歧义才问。屏幕接管全屏使用真实屏幕内容框过渡，见`skills/fred-remake/references/device-camera-rhythm.md`。

### 继承实际末态再交给前景

在既有 `boundaryContract.enter/exit` 记录实际源时间、滚动、相机与载体几何，沿 `sourceMapping` 声明源身份、全局锚点、源入点和速度。`scene.py` 带出邻段已声明映射和边界，不从相同截图推断连续播放。

`templates/components/component-adaptation.ts` 的 `mediaTimeAt` 用全局帧算源秒数，`continueMediaMapping` 在真实交接帧建立下一载体入点，支持继续、改速和显式rate=0保持；只解决恒速区间及分段改速的时间连续，不读取素材、不推断滚动/相机、不替代原生取帧与接缝审看。加蒙版不自动停帧或重启源时钟，有目的的保持仍可采用。


“在上面基础上”“上面加蒙版”“从画布提起再归位”先检查是否延续同一对象。若是，下一段承接实际输出末态：源文件与源时刻、页面/滚动位置、相机位置与透视、对象尺寸/层级，以及继续播放还是有目的的保持，写入现有handoff与媒体映射。不能只复制相同布局，重新挂载后把源视频或相机回到起点；新增前景负责接走观点，底层按当前语义继续或停稳。

画廊中提起的视频来自当时真实槽位与源时间；归位时对齐仍在推进的画廊状态，不返回过时截图。需要尾态截图时，从当前实际渲染状态取帧并核对，辅助composition的[时钟范围](references/render-and-delivery.md#辅助composition取帧的时钟范围)也须正确。接缝两侧比较真实UI、滚动位置和相机/对象几何；发现跳页或重置先修来源与时钟，再决定是否需要有职责的转场。

## 黑白毛玻璃负责从材料转向观点

1. 让观众认清当前材料；上游已建立的界面、照片或设备直接承接，无需重复重开。
2. 在前一帧同一媒体状态上减弱背景干扰，按实际对比选黑/白蒙版与适量模糊。黑蒙版可承载清晰白字，白蒙版可让黑模块/窗口接管；不固定全片底色。
3. 保持前景文字/Logo清晰；按本句出现、归组、停稳、替换或退出。同语义组字体一致，整体重心与底部留白协调。归组总结可按当前语义使用窗口型模块与分行文字，处境列举可使用逐项胶囊；X019/R053是可检索关系，不是固定组合。
4. 下一句仍依赖材料时恢复清晰；需要交接时沿现有设备/内容状态衔接，不突然重开一个无关背景。

蒙版不能把前景文字与角标一起糊掉；全屏遮罩覆盖最终画布，设备内遮罩与屏幕裁切共用几何。背景动作是否继续由语义决定：已要求“持续动着”时保持播放；需要固定底图时才冻结，不能把加蒙版默认等同于截图。查询T07可取失焦与前景接力的准确动作参考，不能把它当作已经参数化的通用滤镜。

多次使用毛玻璃可以成立；检查每次是否接走新的内容重点。不用固定透明度、固定出现秒数或次数上限替代实际可读性判断。

## 产品外壳 + 讲解内容（124 期）

讲解内容需要放大看（几套方案并排、物料一个个弹出），同时又要让观众觉得“这是在产品里发生的”时，不要把真实全景硬缩，也不要把内容放在白底上：

1. 截一张产品真实界面（同一个视口尺寸，4K），保留标题栏、工具条、缩放比例、输入框这些外壳；
2. 把内容区盖成产品自己的底色（取截图里的实际像素值），只剩纯底；
3. 讲解内容按原本的尺寸和动效放进内容区（内容坐标整体映射进去，不另外缩小一套）；
4. 外壳和讲解内容在同一帧里一起入场，接下来如果要回真实截图，用同一个外壳过渡。

Fred 的说法是“用这张图，但是把里面的内容清掉，还是用上一版的尺寸跟动效”。参考实现：124 期 `ep124-v1/src/scenes/board.tsx` 的 `FakeCanvas`（外壳 = 豆包“全屏查看”画布截图）和 `fakeMap()`（内容 → 屏幕坐标，给光标、标注定位用）。另一种做法是在真实截图上把未生成的格子盖掉、到点在原位置弹出（同文件 `FSCanvas`），适合内容本身就在画布上排好的场合；Fred 这期选的是前一种。

## 同一个输出里核对

检查最终视频中的原图/录屏身份、横竖比例、有效UI、源末尾、进入与退出、媒体时钟、外框连续、文字完整、角标局部对比和听得见的动作声音。优先看用户指出的真实时间窗口及相邻接缝；修改播放方式后复核保护层。交付分辨率与来源分辨率分开记录，放大的1080p不能标为原生4K。

### 辅助composition取帧的时钟范围

提取尾态或局部预览时，先核对请求输出帧如何经过Sequence偏移、Freeze/内部相机时钟和源媒体映射，再设置辅助composition的总长度。Remotion的时间上下文可能把超出总长的帧夹到末帧；一帧取图composition也可能将所需尾帧夹回0。辅助总长须容纳所有实际求值时钟，实际渲染范围仍只取需要的帧，不为此延长正式时间轴。

PNG成功输出不证明尾态正确。对照当前视频同阶段的真实内容、相机与滚动位置，记录请求帧、实际映射和辅助总长；取出的帧若被用于下段背景，还要复核交接两侧。具体帧数留本期，不写成固定辅助长度。

## 选择执行位置与时钟

用户当前指定本地就本地，指定云端就使用已授权云环境；切换位置不改变本期素材、字体、帧率、时序或认可范围。本地任务不执行上传、云实例和云目录准备。以下快照/服务器步骤只在云端执行时读取。

8个独立浏览器×每个2并发页面是既有测试起点，browsers、concurrency、GL后端通过job配置选择，记录实际值；不是所有工程必须满足的硬指标。沿用已授权服务器并检查资源，不能把一个浏览器concurrency 16称为8×2，也不为提速改字体、模糊、内容或帧率。只有核验过的实际后端才写GPU生效。

既有工程优先复用该内容已验证稳定的并发与渲染后端；若此前已降并发或使用软件渲染解决异常，不在有限返修时擅自恢复更激进配置。新工程按实际字体、模糊、媒体负载验证；记录实际使用值与失败证据，不把单期配置升为所有新片的固定值，也不凭偶发坏帧猜测GPU为根因。

分块视频去除AAC后拼接，每块concat duration按实际帧数/fps计算，最终MP4使用能精确表达当前帧间隔的timebase（当前60fps链路为60000），完整混音只合成一次。分块内部PTS已失真时不能靠最终timescale或-c:v copy恢复，须按实际异常修复并复验。若 composition 内含必要音效，先导出全范围混音，不能用只有口播的外置文件替代。没有声音的内部诊断与用户要求的正式无声交付分别标明，不能漏掉正式口播。

### 换录音与合并时再核对全局时间

最新WAV与SRT一起锁定；文本几乎不变也需核对每句起止、段长、重点词、段间停顿与结尾。重新映射受影响动作、源录屏、局部字幕及SFX，不以统一偏移、整段拉伸或只换音轨代替对齐；合并句还需检查句内重点。保留未受影响画面与认可设计。

合并前明确每段全局范围及原始gap归属，按实际语义选择延续尾态、过渡或保留停顿，不默默删掉间隙。视频流参数兼容才copy；尤其检查短gap与分块边界的PTS/DTS、精确帧数和实际播放，不能把容器拼接成功当成声画连续。

最终混音要包含所需口播、源素材声音和后加音效；检查源身份、实际尾部、起点、时长与关键落点。发现固定偏移先区分裁切、处理延迟与变速；只有证实后补偿，不把历史样本数写死。最终封装避免在本链路使用会提前结束音频的`-frames:v`，用明确时长及视频帧数验证；独立视频编码可按帧限制。技术异常与工具边界见云渲染的[故障定位](../cloud-render/references/diagnostic-boundaries.md)。

| 新一期关键帧先审 | 新制作先完成实际风险的代表镜头，先交真实关键帧给Fred确认；内部看清短动画表达、声音与接缝后继续，不默认新增用户动态样片确认。共享formal按已确认制作流程及当前制作请求中的实际输出授权记录direct-output，注明只确认过关键帧，不能伪装样片已获认可；这是既有执行器的授权映射，不新增用户审批，也不把Manifest的standard流程改成跳过关键帧。预览可为当前有效规格，不限定必须另做1080p。 |

技术检查针对实际产物：本地核对规格、时长、帧数、音轨、PTS和完整解码；云端下载另核对两端SHA256。导出前检查不冒充最终文件检查。最后补帧、拼接或重新编码后，重新计算hash与相应完整性检查。

默认创意审看覆盖本次完整语义窗口与受影响交接：实际存在的最长文字、跨行高亮、最大特写、蒙版生命周期、关系线初态、换词与角标/字幕区域。有限修改保护其他已认可区域；没有使用的效果不补做样例。用户明确要求自己看、跳过这类审看时，如实标注pending/未审看，不报告视觉PASS或额外等待确认。

多状态复刻带最终口播按1×看完整语义段，核对动作何时到位、完整文字能读多久、口播换了意义时画面是否推进、前后对象是否自然接走。静态分镜齐全、边界像素相同、低清无声诊断和动态采样都不能代替该检查。补总结先看完整操作及结果，再看新增短项和下段接缝；不能为了总结提前截断原演示。用户已要求代码调整后直接正式云渲染、下载后检查时，不追加云端试片或用户动态确认；按真实输出授权和必要技术校验执行，下载后检查当前文件并局部返修。

横版使用[得意黑字幕模块](references/landscape-subtitles.md)时，字幕 cue 对齐最终音轨/SRT；代表镜头及正式文件检查最长字幕、实际盒宽/双行、胶囊和卡片的完整运动包络、上下段首尾态与角标。全屏媒体可延伸至底部，但其信息区仍须可见。检查记录绑定当前文件版本，不把字体加载或技术解码当成视觉避让通过。

最终文件全帧技术异常扫描按`skills/fred-remake/references/render-failure-checks.md`；异常处理以当前授权与实际症状为准，不把预览文件检查套到新编码上。复杂字体/模糊的局部缺失需看具体ROI；整屏亮度、代理播放器和Contact Sheet都不能证明美术质量。

使用WebGL/Three.js承载页面或输入区时，检查实际纹理ROI及候选前后帧，并与源素材同时间状态对照，区分源坏帧、取帧映射错误、异步纹理未就绪和最终合成缺失。只有证据指向资源就绪/提交时序时，才在该实现中等待相应资源并验证渲染提交完成；设置了屏障或延长等待不等于修复，须复查真实输出及受影响边界。纹理同步、后端和并发是针对已定位故障的选择，不是所有工程的默认配置，也不以整屏平均亮度正常代替小区域检查。

技术空帧、语义空场和有目的阅读分别判断。动态采样只能证明所采位置的变化；`requiredChangeEvents`不得超过`sampleCount - 1`，配置不可能达成时先修配置。小区域动作被整屏均值漏掉时按真实cue与ROI复核并记录证据，不靠增加无意义动作凑阈值。不要把采样通过写成美术或用户认可。

## 返修如何限制范围

先读取真实最新反馈来源；浏览器localStorage/IndexedDB中的用户判断、意见和贴图与HTML内助手写的advice/版本说明分别处理。仅抓静态HTML且textarea为空时，不声称已读到最新意见。

用户每次指出问题时记录原话、源版本/hash、精确时间、症状、保留对象、目标层和验收画面。先收集本轮所有明确问题，定位原因，再一次实施相关修订。被保留的视频/声音/布局不随意更换。

先区分过多状态、缺少语义推进、动作拖慢、几何错误与媒体映射错误，按问题选择删格、重排动作或重新选适合的已认可组件，不只给失败版加淡化。保持口播/字幕/总时长的画面返修不擅自剪音频；用户明确授权删句时才转入音频与字幕流程，并重新映射下游。

动作落点改变时，音效跟随真实入场、命中、收束与交接局部重绑，控制突响和密度，不强制每个元素都配声音。已混完整音轨先保护未改的口播、源声及BGM，仅调整受影响SFX；原PCM可精确对照时记录保护窗口，最终AAC另测。完整已混音不重新铺音乐或处理人声，私人音乐按原规则仅本机合成，不上传云端。

允许复用已验证未改帧，补渲受影响范围及邻接；源码共享导致下游首态变化时计入范围。只有压缩 MP4 可用时说明拼接/重编码影响，不冒称无损。保持帧数和语义时钟，不用删帧、慢放、插帧或模糊掩盖异常。

### 烧录字幕与局部合并

多来源合成先按每段当前有效文件身份建表，不能用某个聊天的旧整片覆盖其他聊天的新局部。除分辨率/fps外，先核实际timebase、帧数/PTS、GOP/IDR和流参数；按可验证的共同时间基准封装，不能把帧率相同当时钟相同，也不假定所有GOP等长。替换后核实际最终文件的准确修复帧与邻接状态，保留原完整音轨；源自带动作遮挡与真正缺画面分别诊断。


先确认字幕是外挂还是烧录。外挂文字可更新字幕轨并重新封装；烧录文字需要改当前cue源码并只渲受影响范围，保护同一基线的画面、字体、时序、旧修正和完整混音。确认范围时检查同产品的全部指代，不只改用户截图那一帧。

cue按全局`[startSeconds, endSeconds)`显示时，首帧为`ceil(startSeconds * fps)`，结束帧为`ceil(endSeconds * fps)`且不包含；以实际组件选择逻辑和固定帧率复核浮点边界。Remotion右端包含，提交时用`endFrameExclusive - 1`。局部渲染的媒体与字幕仍沿原全局时钟，不能从片段0秒重新选cue。

已有完整视频时，优先复制未改视频流与完整音轨，替换准确帧区间。任意切点不一定可直接copy：查实际源关键帧，必要时仅编码切点邻近GOP的桥接，再按每段真实帧数/fps拼接；流参数不兼容时选择必要编码并如实说明，不声称整片无损或从未编码。音轨默认用原完整混音一次封装，避免分段AAC重复编码引入间隙；只有用户要求音频变化才改音轨。

检查实际最终MP4的完整解码、规格/总帧数、PTS连续性、两端替换边界及新字幕；未改画面对照有效基线，直接copy的音轨核对流身份。先交局部片段还是完整合并以最新请求为准，用户后来要求完整视频时直接完成合并，不再要求其手动剪辑或重渲整片。

“使用copy”不是保护范围的完整证明。可直接复用的区间检查实际IDR/GOP、参数集、像素格式/色彩和时间基准；拼接工具是否自动转换也以实际packet为准。需要保证压缩流原样保留时，核对未改视频packet payload与完整原音轨packet内容/时间戳；无法原样copy时如实记录必要的桥接编码，不宣称整片无损。追加小改只使完整依赖受影响的补丁失效，能证明源码、输入与配置未变的已验证补丁可继续复用；冻结硬链接不原地改写。

媒体异常先对比最终输出与源素材同时间状态；源正常不代表本次合成正常。需要原生源帧缓存时保持源尺寸/帧率、准确入出点和全局时间映射，再按时间线选源帧，不能删帧、光流插帧或改变源动作掩盖故障。此方法是已验证局部修复路径，不代表所有视频都要抽帧，也不证明不同帧率是唯一根因。

用户描述“某一分钟附近闪了几下”时，先在该完整时间窗口扫描实际最终文件并定位帧号，再看候选前后连续状态和源片同时间。白底讲解、主动显隐和真实素材黑场不自动算故障；整屏指标只能找候选，还要看媒体ROI是否空白、短时重置或残留。补渲范围按实际首尾态依赖确定，可包含邻接段，不固定只补某个帧数。重查修复后最终MP4同一帧及新旧切点，保留总帧数和完整原混音，不能删帧消闪或只验证补丁文件。

### 验证实际运行入口

# 逐段审看：建议、真实关键帧、视频

生成前必须通过[组件库交付门禁](references/library-delivery-gate.md)。生成器现在会直接检查当前Manifest，失败时不覆盖已有HTML；即便首次打开建议视图，只要页面包含Remotion关键帧，也执行关键帧级检查。自定义前端与聊天建议同样必须运行门禁，不能换入口绕开。未通过的旧页面不会因此被自动重做或取得新认可。

同一期沿用一个页面、同一份当前 Manifest，分成三个视图。它规定协作方式，不规定镜头数量、构图模板或每期必须出多少张图。

1. **图文建议**：助手先按逐字稿提出制作方式、原因和画面方向；Fred 选择或改动。助手建议不会预先勾成用户选择。H3、Seedance 等生成视频都可归入 `generated-video`，具体工具及既有外部素材由本段方案说明。
2. **真实关键帧**：用准备继续制作的实际 Remotion 源码生成图片，连同当前字幕和角标一起看。每帧有完整原文、时间、图片和可填写的图文意见；确认只覆盖这张静态画面。关键帧按语义、稳定阅读态、关键运动中间态及接缝选取，不固定 140 张或均匀抽样数量。
3. **视频审看**：方向和关键帧处理后看正常速度视频，检查节奏、声音、运动和衔接。当前视频排第一，历史版本可展开。静帧通过不能证明动态通过。

三列固定为逐字稿／当前视图的真实素材或建议／用户选择与修改意见。已有明确选择、有限返修、当前直出授权按主流程处理，不为了此页面重新询问。路线、候选方向与实现的关系见[路线与分镜选型](references/route-and-storyboard-review.md)。

## 保存、导出与返修

长片按原逐段口播对应播放：每行可提供准确起止的独立短段文件和修改前版本，避免每行挂整条4K视频并同时预载/解码。按实际前端能力懒加载、限制并播并保留原行入口；用户要求逐行播放器时不擅自改成共享单播放器。段视频、关键帧、完整最终文件与版本标签分别核对hash和全局范围，不能用旧关键帧替代新视频的反馈。当前公共台的短段准备由prepare_review_segments.py执行；静态HTML生成器本身不自动切片。

静态HTML页面支持文字、粘贴图片、插入图片、图片放大、筛选和导出。判断使用“保留主体／需要修改／先跳过”。“保留主体”同时有非空文字或图片意见时，显示“保留主体，仍需修改”，不会自动变成最终批准。即使备注是表扬，是否属于明确认可仍由主流程结合原话判断，不由前端猜测。

每条反馈绑定 `episodeKey + stableId + view + itemId + identity`。`identity` 包含真实资产文件 hash、当前原文/时序和 `scene_review_signature`。换图、换素材版本或当前语义上下文改变后，本版判断置空；以前的文字和图片保留在历史中，不通过同名 `frame-01` 继承认可。三个视图各自保存，关键帧确认不影响视频判断。

以下保存说明及schemaVersion=5仅适用于静态HTML生成器；公共台使用上面的磁盘保存和schemaVersion=2。静态HTML的浏览器文字数据保存在 localStorage，意见图片在 IndexedDB。保持同一页面路径、浏览器和 episodeKey；file 与 localhost、不同端口/浏览器的存储不可视为共享。旧版审片页的数据保留为 `legacyFeedback`，不迁移成新画面认可。每轮操作后导出留档；当前页面没有导入功能。

### 容量失败与恢复边界

静态HTML的浏览器存储与公共台的磁盘服务器是不同能力；不要把HTML当作自动具备磁盘恢复/导入，也不要重新为每期写专用服务。长期多版本审看时先核对实际持久化实现，不把本期专用功能写成公共已支持。

- 保存须处理 `QuotaExceededError` 和图片写入失败，用户不能看到假的“已保存”。保留当前内存中的意见并提供实际可用的导出/备份方式，避免失败后继续操作覆盖唯一副本。
- 同一源码清单在多帧重复时可做无损引用去重，验证pack/unpack后逐条身份、文字、图文顺序、图片和历史完全一致；不能通过删历史或丢sourceFiles腾空间。
- 已实现本期文件备份时用临时文件、完整写入后原子替换；恢复按 `episodeKey/stableId/view/itemId/identity` 合并，不覆盖较新本地意见，也不把旧版选择转成新版认可。按真实能力执行，不新增强制换服务器流程。
- 更新入口前后核对记录、非空文字与贴图的身份/内容；恢复成功不能只数条目。取证JSON pointer允许对象键与数组索引，版本/原始文件hash继续核验，未知用户发言时间仍保持空值。

导出 `segment-review-feedback.json` 使用 `schemaVersion: 5`：

- 顶层 `episodeKey`、`exportedAt`、`records`、`legacyFeedback`、`savedToManifest: false`。
- 每条 `records[]` 保存 `stableId/view/itemId/identity`、`artifact`（图片、视频、候选的实际路径/hash）、`context`（原文、时间和上下文签名）。`current` 区分当前记录与历史。
- 助手字段为 `assistantSuggestion/assistantRecommendation`；用户字段为 `selectedRoute/userSelection/choice/note/content/images`。`userSelection` 含准确候选 ID 和图片 hash，全部不选为 `{ "decision": "none" }`。
- `needsChanges` 表示仍需处理意见；`approvalScope` 只说明方向、静态帧或视频审看范围。页面始终不自动宣称 `animationApproved`，也不编造 `confirmedSource`。
- 图文 `content` 保留光标顺序，意见图片以 data URL 导出；历史版图片同时保留。

助手必须读取本轮导出，核对实际资产和上下文再合并进当前 Manifest；只读 HTML 内的建议不算读过用户反馈。未选择、未填写不等于同意，也不能覆盖已有真实批准。对“保留主体但要改”先处理可判定的局部意见，再更新相应帧/视频；保留区不重新设计。动态短窗与整片声音/接缝检查继续按原门禁执行。

## 每次接手与每轮反馈

现有跨期判断见 [历史偏好与防错规则](references/feedback-rules.md)；结构化源为 `feedback-rules.json`。每条保留触发场景、喜欢的关系、要避免的症状、不要泛化的边界、检查方法和原话出处。规则修改后验证 `scripts/verify_feedback.py`，运行 `scripts/build_reading_guide.py` 重建规则阅读版与完整说明，再同步全局轻量文件。证据验证不代替视觉审看。

本期保留一份当前 Manifest 与交付索引，反馈写现有修订清单或 `feedback.jsonl`。每条记录应能定位：用户原话及消息来源、所指文件/hash、时间范围、问题对象、保护内容、本轮调整、实现版本、检查证据、结果与仍待确认内容。 同时读取按钮判断与文字意见；keep/approved与明确待改内容并存时，不能直接登记整段认可。方向选择、真实关键帧确认、内部动态检查和最终视频认可分别绑定实际产物。

没有用户消息精确时间时记 `recorded-at`，不把执行时刻伪装成发言时间。不要覆盖旧反馈或把反复修改压缩成“用户喜欢此风格”，导致不知道最后取舍了什么。

新认可按当次明确范围记录；旧批评保留日期与版本，不继续冒充当前状态，也不倒改所有历史版本的认可。

历史复核新定位到准确原话时，在本次审计保存原始路径/物理行/实际时间和摘录，不倒改旧认可事件。按当前要求、最新准确选择、同一对象后续取舍判断；助手诊断单独标记。不同版本、阶段或用途的意见不能互相无条件覆盖：例如反复毛玻璃与适量重点蒙版、早期解释动画与后期真实产品截图、同轮统一与跨组变化。

用户要求整期复盘时，从当前场景清单串联早期关键帧、各轮真实意见、最终实际画面和实现调用，包含无备注的保留段及明确删段，不能只总结最后一轮投诉。旧目录缺失时保留归档原话与执行回执，标出无法重读的图片/源码范围；不按目录名推断版本。逐段抽帧对照属于静态抽样复盘，连续动态、声音听审和技术验证各自记录。经验优先补已有规则的触发、检查与边界，单期参数、选图和失败过程留在本期证据索引。用户明确要求跨期固定复用时保存对应公共组件、准确参数与授权范围；108 v9主播放外壳的当前默认见[全屏主视频组件](references/fullscreen-video-window.md)，不继续将这项明确偏好限制为单期参数。

评价“返修少／这次更好”时，区分用户主要创意返修、同轮局部补充、助手内部修复与上游组件研发；版本桶数不直接等于返修轮数。结合实际修改范围、素材准备程度、成熟模块承担的内容和新设计难度判断原因，不能仅凭轮数归因于流程改善。沉淀可复用的决定与检查，不设“每期两次”的目标，也不把本期现成媒体比例、场景数或组合固化；既有成片与批准状态不因复盘改写。

## 状态分开保存

| 状态 | 可以依据什么写入 |
| --- | --- |
| generated / rendered / downloaded | 实际任务返回、产物与本地校验 |
| internal-reviewed | 助手实际检查范围、方法和证据 |
| user-accepted | Fred 的明确认可原话及准确对象/范围 |
| source-preserved | 源文件、依赖和 hash 已核验 |
| parameterized / build-passed | 新 API、不同参数与构建检查 |
| reusable-visual-reviewed | 新内容短样的实际视觉检查；单独记录是否获用户认可 |
| sent | 实际发送目标、文件身份和回执 |

整个组件、某个局部动作、首帧与完整视频的认可范围不同。默认继续尊重选片台的 keep/optional/drop；本期“可以用”不自动覆盖已有公共排除项。

## 何时沉淀新公共能力

Fred 已授权持续沉淀，允许把通用修复和可复用方法保存成候选；用户喜欢的范围与是否跨期使用仍需真实依据。把当前源片路径/hash、起止帧、实际调用函数、依赖、可变参数、保留关系、已知限制与验证证据一并登记。

优先提取多次实际使用且重复返工的能力：跨行原文聚焦、ROI 多处特写、屏幕接管、关系线初态、同槽替换。参数接口随实际需求形成，不为每个旧片段创建一个名字相近但无实质复用价值的组件。

新适配用不同长度/换行的文字、不同图片比例、不同 cue 检查；参考帧复现只能证明该样例。修复线帽残点时留下进度零与第一可见帧的检查，修复跨行焦点时用跨行/重复词/长短词，而不是只增加一句禁止项。

新版本独立保存；旧项目锁旧源码和依赖。通过检查后更新轻量索引的“可用性”，用户实际认可后更新“偏好”；两者不互相代替。凡选择 revision 改变，先保存旧快照再更新 registry，不能直接改旧记录抹掉来源。

## Skill 维护边界

日常新视频不重写整份 Skill。单期素材与记录在本期，跨期候选在项目依赖目录，稳定通用判断进入本 Skill 的对应 reference；无需把完整聊天、视频文案或所有失败尝试塞进主文件。

用户要求沉淀 ChatGPT Pro 生图与复刻方法时，维护[ChatGPT Pro 分镜探索与 Remotion 复刻](references/chatgpt-pro-storyboard-replication.md)。沉淀触发条件、提示词、来源与认可边界，以及从多状态取舍、口播动作编排、连续对象、阅读窗口、真实媒体保护到局部返修和完整交付的方法；规划辅助使用[多状态动作模板](templates/pro-storyboard-motion-plan.md)，写回现有Manifest。具体场景的原话、prompt、会话、图片hash、用户选择、实现文件、单期参数和失败过程留本期。聊天中提出过生图请求不等于图片已生成、用户已认可或已进入成片，必须以本期生成清单和实现证据分别确认。

复盘反复返工时，先检查已有规则是否实际到达执行者、当前动作是否混入旧版本、检查是否只覆盖字段而未对照真实要求；不要默认继续增加负面提示词。工具漏传字段或允许不可能配置时，以失败回归修工具；审美与语义问题用准确参考和真实输出对照。规则级修复不会追认旧画面，也不自动改写冻结成片 Manifest。当前要求传递与代表段做法维护在 `production-defaults.md`，不另起同义质量体系。

用户认可的完整模块与局部能力都可按实际用途沉淀和直接复用，保留准确来源与认可范围；不强制拆成局部，也不把整期搭配固化为所有新片的默认方案。按storyboard.md判断当前内容职责、动画推进和同等质感，不建立近期使用禁用表、冷却期或固定创新比例。

全局注册镜像主文件、references、脚本、模板；大资产和 node_modules 只保留项目实体。修改流程时同步项目 AGENTS/PROJECT 的入口，核对相关全局文件 hash。已停用的 Deck/H3 默认路线不因为一次调用专项工具就自动恢复。

本流程不自动改写 `~/.codex/memories/`；这里只维护用户要求的生产 Skill 与本期/组件记录。

## 按表达关系整理新参考

先将用户截图/编号绑定准确成片hash，再记录排除；同一条的多张截图只算一个选择。原片受到保留、复刻受到保留、新内容通用API通过检查三个状态分开。

在同一 `preferred-motion/catalog.json` 中登记新条目，选择来源保存在不可变 `selectionSources` 证据快照；依赖 registry 只锁路径/hash，不另建可独立改写的批准台账。旧 selectionRevision 继续指其原 picker，新用户事件用独立来源ID与catalogRevision表明，不伪装成旧选片台的新点击。

去重比较用途、主动作顺序、对象关系和现有参数；配色、圆角、胶囊只是表面。明确重复只保留一个默认代表，旧编号记录canonicalId；有差异却只是同名时保留不同能力。跨旧库合并要读实际视频和实际挂载源码，不只比名字。未实现的变体参数应标待适配。

加入新参考后补齐sceneTypes/useWhen/tags/sourceCode/依赖/限制，验证scene-type过滤、旧编号别名、drop排除、来源哈希变化拒绝、孤立源码构建、实体视频与素材哈希。同步项目和全局轻量Skill；大资产只在项目实体。最后生成可浏览文件架，不能只交付一份说明文档。

不同Remotion锁定版本要在独立进程中构建，不能把旧库4.0.519和V2/本批4.0.473加载到同一Node进程。`verify_source_bundles.cjs`按bundle启动进程；`verify_dependencies.py`另查完整素材库存、合法场景类型、合并目标和实际注册编号。沿用原库的选择计数单独核验，新集合使用当前聚合计数，不覆写旧选片事实。

## 局部过渡学习

对象缩放、让位和交接作为局部动作记录到transition-patterns.json，绑定原片内部起止帧、准确hash、源码位置、可迁移关系与已知限制；方向变化按变体处理。状态仍由同一catalog决定，排除和合并记录不借局部索引回流。新源片hash变化要重新检查。更新学习页与轻量查询后同步项目和全局Skill，不把示例时间硬编码为新期节奏，也不把未实现的参数称为公共API。

文字呈现维护在text-patterns.json：区分字符数变化、clipPath揭示、文字流translate、opacity淡化与数字插值。新形式补源片区间、源码机制及实际边界，不把文字载体移动误记成字形动画；正文组件入口同步链接这一份索引，避免复制批准状态或另起相同资产库。

## 完整组件与局部取舍分离

前端复看全部完成后，保存review revision、fingerprint、完整取舍与当时前端引用快照，核对后更新同一catalog的selectionSources/catalogRevision；保留旧picker revision和旧批准历史。整期选段以status记录排除并保留准确源范围，默认查询与前端只显示keep。局部明确保留可在源完整组件被排除时继续使用，但必须由对应文字/过渡条目的selection绑定用户快照、decisionKey和hash；只批准准确局部，不恢复完整组件。同步源注册、文件架、索引及依赖hash，归档已应用取舍，前端换到新库。

## 避免重复与历史规则膨胀

- `production-defaults.md`负责选型默认值；`storyboard.md`负责原文/时钟/分镜结构；`scene-routing.json`只映射类型与附加项；`feedback-rules.json`保存有证据且有范围的偏好；`content-to-component.md`负责源码归因与质量评估；`render-and-delivery.md`连接交付状态。专项实现细节只在其所属Skill维护。
- 主入口与阶段文档可做短摘要和链接，不复制另一套参数或硬门禁。`feedback-rules.md`和完整说明是自动生成视图，只改源文件后重建，不分别手改。
- 新规则先分清用户明确固定项、可覆盖的默认值、场景条件与历史症状。单次“不加某词”“五秒播完”“只改为白色”留在该期；只有跨内容仍成立的方法才入公共规则。旧批评保留版本与日期，不把历史例子的对象数、时长或布局变成全局禁令。
- 每次沉淀同时保留有效的相反取舍：过程需要变化，结论可纯文字；操作需要推进，阅读可停稳。新经验优先补已有规则的触发、检查和边界，不凭一次抱怨新增全局配额或审批。审美观察留在内部审看，只有可客观验证的问题进入代码校验器。
- 前端意见以`user-feedback`单独归因，保存原快照/hash、JSON位置、stableId、判断和所评版本；未知发言时间保持空值，以`recordedAt`表示取证时间。原话及单期证据留在该期，通过项目`00_每期项目`入口检索；不复制成公共批准案例。
- 文档说允许而脚本拒绝时，用最小案例定位执行范围；修正后同时保留允许案例和真实风险拒绝案例，不只删提示文字。代码门禁只陈述它实际验证的边界。
